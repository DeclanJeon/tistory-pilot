analytics를 붙이고 나서야 보인 것들

PonsWarp에 analytics를 붙인 일은 화려한 기능 추가가 아니었습니다. WebRTC 전송, 저장 완료 핸드셰이크, WASM 코어, Rust signaling 서버, Cloud Drop, 결제와 entitlement까지 지나온 뒤에 붙은 측정 계층이었습니다. 기록상으로는 2026-06-08 `d88a625 Enable production traffic measurement with GA4`가 그 지점입니다.

이 커밋은 파일을 더 빠르게 보내게 만들지도 않았고, Cloud Drop 용량을 늘리지도 않았습니다. 하지만 제품을 보는 방식은 꽤 크게 바꿉니다. 그 전까지 PonsWarp는 “이 기능이 기술적으로 가능한가”와 “이 흐름이 설계상 말이 되는가”를 중심으로 움직였습니다. analytics가 들어오면 질문이 달라집니다. “실제 사용자는 어디로 들어오고, 어디서 멈추고, 어떤 선택지를 보기도 전에 나가는가”를 봐야 합니다.

💡 이 글은 GA4 설정법을 설명하는 글이 아닙니다. PonsWarp가 제품화 막바지에 analytics를 붙였다는 기록을 기준으로, 측정이 늦게 들어왔을 때 비로소 보이는 제품 구조와 판단 비용을 정리합니다.

🧭 당시 제품 상태: 기능은 많았지만 관찰은 늦었다

PonsWarp는 처음부터 측정 중심 제품이 아니었습니다. 시작점은 대용량 파일을 브라우저에서 직접 보내겠다는 기술적 실험에 가까웠습니다. `ad322f3`의 첫 커밋 이후 곧바로 `638bc83`의 메모리 폭발 방지, `21dc9ba`의 수신 저장 완료 핸드셰이크, `2def330`의 TURN 동적 설정, `db175bf`와 `4650d02`의 청크 순서와 파일 손상 수정이 이어졌습니다.

이 구간에서 중요한 것은 실제 사용자가 어디서 이탈하는지보다, 파일이 깨지지 않고 끝까지 닫히는지였습니다. 그것은 당연한 우선순위였습니다. 파일 전송 제품에서 무결성이 흔들리면 analytics를 붙여도 의미가 없습니다. 사용자는 “몇 퍼센트에서 나갔는가”보다 “받은 파일이 맞는가”를 먼저 판단합니다.

그 뒤에는 성능과 저장 경계가 들어왔습니다. `949d921`의 파이프라인 병렬화와 이중 버퍼링, `54cf5f4`의 backpressure, `09161ce`의 RTT 기반 동적 혼잡 제어는 브라우저 안에서 전송을 버티게 만드는 작업이었습니다. `pons-core-wasm`은 `15aef19`로 시작해 ZIP64, 재정렬 버퍼, Merkle Tree, 파일 서명, zero-copy, crypto 같은 바이트 계약을 맡았습니다.

그러나 이 모든 것은 내부 정합성의 문제였습니다. 시스템은 점점 더 똑똑해졌지만, 제품은 여전히 사용자의 실제 경로를 충분히 보고 있지 못했습니다. 누가 direct transfer를 시도하는지, 누가 Cloud Drop을 선택하는지, pricing 화면까지 도달하는지, 모바일 수신자가 어디서 멈추는지는 별도의 관찰 문제였습니다.

📦 제품화가 만든 측정의 필요

2026년 5월 이후 PonsWarp는 기술 데모에서 서비스에 가까운 형태로 이동했습니다. `4847872`는 delayed downloads를 위한 async Cloud Drop을 붙였고, `b6f3ea8`은 Cloud Drop pricing page를 만들었습니다. `f8f2120`은 Stripe Checkout으로 entitlement를 발급하려 했고, `2e4593d`는 Cloud Drop billing을 PayPal로 돌렸습니다. `3628858`은 대용량 Cloud Drop upload를 multipart resumable 구조로 만들었습니다.

이 흐름은 단순히 “기능이 늘었다”가 아닙니다. 제품의 질문이 바뀐 것입니다. direct transfer만 있을 때 핵심 질문은 두 사람이 동시에 온라인일 수 있는가, 네트워크가 붙는가, 저장이 끝나는가였습니다. Cloud Drop이 붙으면 질문은 달라집니다. 보내는 사람은 상대가 나중에 받아도 된다는 가치를 이해하는가. 무료 10GB/24시간 정책은 충분히 관대하면서도 비용을 감당할 수 있는가. 유료 결제는 언제 등장해야 거부감이 덜한가.

`a004c91`은 Free plan을 first-class cloud policy로 노출했고, `212d751`은 gated account와 billing surface를 비활성화했습니다. 이 두 기록은 특히 중요합니다. 무료 정책과 결제 표면이 단번에 고정되지 않았다는 뜻이기 때문입니다. 정책은 코드로 표현됐지만, 실제로 맞는지는 사용자 흐름을 봐야 합니다.

analytics가 필요한 이유가 여기에 있었습니다. 가격표를 만들었다고 가격 전략이 검증되는 것은 아닙니다. PayPal entitlement가 동작한다고 사용자가 결제할 이유가 생기는 것도 아닙니다. Cloud Drop upload가 resumable이라고 해서 사용자가 direct transfer 대신 Cloud Drop을 선택할지도 알 수 없습니다. 제품화 단계에서는 기능의 존재보다 선택의 흐름이 더 중요해집니다.

🔎 analytics가 보여주는 것은 정답이 아니라 빈칸이다

GA4 production measurement를 붙였다고 해서 갑자기 제품의 답이 나오는 것은 아닙니다. analytics는 “왜”를 자동으로 설명하지 않습니다. 다만 그동안 감으로만 말하던 빈칸을 드러냅니다.

예를 들어 direct transfer가 제품의 중심이라고 믿고 있었는데 실제 트래픽이 Cloud Drop 설명이나 pricing 근처에서 더 오래 머문다면, 제품 언어를 다시 봐야 합니다. 반대로 Cloud Drop을 수익화의 중심으로 생각했는데 사용자가 파일 선택 전에 나간다면, 문제는 결제가 아니라 첫 화면의 약속일 수 있습니다. 모바일 수신 복귀를 고쳤다는 `8f7299d` 같은 기록도 analytics 없이 보면 기술 수정으로 끝나지만, 실제로는 모바일 흐름에서 어느 정도의 이탈을 줄였는지 봐야 의미가 닫힙니다.

이 지점에서 analytics는 기능 목록 바깥의 계층이 됩니다. React/Vite/Tailwind로 만든 화면, WebRTC와 worker로 만든 전송 엔진, `DirectFileWriter`와 partial recovery로 만든 저장 경계, `pons-core-wasm`과 `ponswarp-signaling-rs`로 만든 코어/서버 위에 “사용자가 실제로 어느 길을 걷는가”라는 관찰 계층이 올라갑니다.

PonsWarp에서 이 계층은 늦게 붙었습니다. 늦게 붙었다는 말은 무가치했다는 뜻이 아닙니다. 오히려 이미 기능이 많은 상태였기 때문에 더 아팠습니다. analytics가 드러내는 숫자는 “어느 버튼이 몇 번 눌렸는가”에서 끝나지 않습니다. 그 숫자는 이미 만들어 둔 기능 중 무엇이 중심이고 무엇이 곁가지인지 다시 묻습니다.

🧱 시스템 구조: 측정은 가장 위에 있지만 가장 늦게 닫힌다

PonsWarp의 반복 구조를 네 층으로 보면 analytics의 위치가 분명해집니다. 1층은 Product and UI입니다. `src/App.tsx`, `SenderView.tsx`, `ReceiverView.tsx`, `CloudSenderView.tsx`가 direct transfer와 Cloud Drop의 선택지를 사용자에게 보여줍니다. 2층은 Browser transfer engine입니다. `simple-peer`, sender/receiver worker, adaptive chunk/batch, AES-256-GCM, ZIP64, backpressure가 전송의 실제 동작을 맡습니다.

3층은 Storage and recovery입니다. `DirectFileWriter`, StreamSaver, File System Access API, high/low watermark, partial recovery가 저장 완료의 진실성을 다룹니다. 4층은 Core and backend입니다. `pons-core-wasm`은 compression, crypto, packet, reordering buffer, zero-copy pool, ZIP64, file signature, merkle tree를 맡고, `ponswarp-signaling-rs`는 auth, billing, database, handlers, protocol, state, `/health`, `/ready`, `/ws` 같은 운영 경계를 맡습니다.

analytics는 이 네 층을 대체하지 않습니다. 하지만 네 층이 사용자에게 어떤 순서로 체감되는지 확인하게 만듭니다. 사용자는 먼저 화면의 약속을 보고, 그다음 파일을 고르고, 연결을 기다리고, 실패하거나 성공하고, 필요하면 Cloud Drop과 가격표를 봅니다. 내부 계층은 아래에서 위로 쌓이지만, 사용자의 경험은 위에서 아래로 내려갑니다.

그래서 측정은 가장 위에 붙는 것처럼 보이지만 실제로는 가장 늦게 닫히는 계약입니다. 이벤트 이름 하나를 붙이는 문제가 아닙니다. 어떤 흐름을 제품의 중심으로 볼 것인지, 성공을 무엇으로 정의할 것인지, 실패와 이탈을 어떻게 구분할 것인지가 먼저 있어야 합니다. PonsWarp는 기술 계약을 많이 닫은 뒤에야 이 질문을 제대로 마주했습니다.

⚠️ 실제 실패 지점: 숫자를 보기 전까지는 모든 선택이 그럴듯했다

analytics가 없을 때 제품 판단은 대개 설계자의 직감에 기대게 됩니다. PonsWarp에서는 direct transfer도 그럴듯했고, Cloud Drop도 그럴듯했고, 무료 10GB/24시간도 그럴듯했고, PayPal entitlement도 그럴듯했습니다. 각각의 기능은 따로 보면 충분히 합리적이었습니다.

문제는 합리적인 선택지가 많아질수록 제품의 중심이 흐려진다는 점입니다. 사용자가 동시에 온라인이면 direct transfer가 좋습니다. 상대가 나중에 받을 수 있어야 하면 Cloud Drop이 좋습니다. 무료 정책은 진입 장벽을 낮춥니다. 유료 정책은 비용을 설명합니다. 모바일 resume은 신뢰를 높입니다. 그런데 실제 사용자가 어느 흐름을 기대하고 들어오는지 모르면, 모든 기능이 “중요해 보이는 상태”로 남습니다.

이것이 analytics를 붙이고 나서야 보이는 것입니다. 측정은 새 기능을 추가하는 일이 아니라, 이미 만든 기능들의 우선순위를 불편하게 재배열하는 일입니다. 어떤 화면은 생각보다 보이지 않을 수 있고, 어떤 선택지는 설명되기도 전에 버려질 수 있습니다. 어떤 기술적 수정은 중요했지만 제품 지표로는 거의 움직임을 만들지 못할 수도 있습니다.

PonsWarp의 기록에서 `d88a625`는 그래서 작은 커밋처럼 보이지만, 제품화 흐름에서는 꽤 늦은 거울입니다. 거울을 붙였을 때 제품이 갑자기 좋아지는 것은 아닙니다. 다만 더 이상 “아마 사용자가 이렇게 할 것이다”라는 말만으로는 버티기 어려워집니다.

🔄 설계 변경: 기능 중심에서 경로 중심으로

analytics 이후의 설계 변경은 코드 구조보다 사고방식에 가깝습니다. 이전에는 기능 단위로 질문했습니다. WebRTC가 붙는가. 저장이 끝나는가. Cloud Drop upload가 재개되는가. 결제 후 entitlement가 발급되는가. 이 질문들은 모두 필요했습니다.

하지만 측정이 들어오면 경로 단위 질문이 생깁니다. 사용자는 어떤 진입점에서 시작하는가. direct transfer와 Cloud Drop 중 무엇을 먼저 이해하는가. pricing은 설득 페이지인가, 차단 페이지인가. 무료 정책은 체험을 열어주는가, 유료 전환을 애매하게 만드는가. 모바일 수신자는 백그라운드 복귀 후 다시 흐름을 이어가는가.

이 변화는 운영/배포 관점에서도 중요합니다. GA4 production measurement는 로컬에서만 만족하는 기능이 아닙니다. production traffic을 봐야 의미가 있습니다. `/health`, `/ready`, signaling room cleanup, billing webhook, resumable upload와 마찬가지로 analytics도 운영 환경에서만 닫히는 계약입니다. 그래서 QA 문서에서 publish readiness를 REVISE로 두는 이유도 여기에 있습니다. 글은 준비됐어도 실제 발행과 라이브 렌더링, 공개 URL, 운영 측정은 별개의 단계입니다.

🧭 지금 돌아보는 판단

지금 돌아보면 PonsWarp에 analytics가 늦게 붙은 것은 이상한 일이 아닙니다. 제품의 바닥이 불안한 상태에서 측정부터 붙이는 것은 허영에 가깝습니다. 파일이 깨지고, 저장 완료가 거짓이고, 모바일이 끊기고, 서버 cleanup이 deadlock을 만들면 방문자 수를 보는 일은 본질이 아닙니다.

하지만 제품화 구간에 들어간 뒤에는 이야기가 달라집니다. Cloud Drop, pricing, entitlement, free plan, PayPal, mobile resume까지 붙은 뒤에도 측정이 없으면 제품은 여전히 개발자의 머릿속에서만 닫힙니다. 실제 사용자는 그 머릿속 순서대로 움직이지 않습니다.

PonsWarp가 analytics를 붙이고 나서야 본 것은 숫자 자체가 아니라, 제품이 이미 너무 많은 가정을 품고 있었다는 사실입니다. direct transfer가 중심인지, Cloud Drop이 중심인지, 무료 정책이 초대장인지 비용 폭탄인지, 결제 표면이 설득인지 방해인지. 이 질문들은 코드만 읽어서는 닫히지 않습니다.

그래서 이 단계의 교훈은 “초기부터 무조건 analytics를 붙여라”가 아닙니다. 더 정확히는, 제품이 기능 실험에서 서비스 판단으로 넘어가는 순간 측정 계층도 함께 설계해야 한다는 것입니다. PonsWarp는 그 경계에 도착한 뒤에야 거울을 달았습니다. 그리고 거울은 제품을 구해주지는 못했지만, 무엇을 모르고 있었는지는 보여줬습니다.
