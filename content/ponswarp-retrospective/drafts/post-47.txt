free plan rollback에서 드러난 판단

PonsWarp가 Cloud Drop을 붙인 뒤부터 제품의 질문은 조금 달라졌습니다. 처음에는 “상대가 지금 온라인이 아니어도 파일을 받을 수 있게 할 수 있는가”가 핵심이었습니다. 그런데 Cloud Drop이 들어오자마자 다음 질문이 따라왔습니다. 이 기능을 어디까지 무료로 열 것인가. 얼마부터 유료로 볼 것인가. 계정과 결제는 언제 등장해야 하는가.

이 질문은 기술 구현보다 늦게 오는 것처럼 보이지만 실제로는 그렇지 않았습니다. 무료 정책은 단순한 가격표가 아니었습니다. 10GB, 24시간, Cloud Drop, 계정, entitlement 같은 단어가 한 화면에 올라오는 순간 사용자는 그것을 내부 실험이 아니라 제품 약속으로 읽습니다. 그래서 `free plan rollback`은 돈을 포기한 기록이 아니라, 아직 감당하지 못한 약속을 제품 표면에서 한 번 내린 판단에 가깝습니다.

💡 이 글은 “무료가 좋다”거나 “유료화가 나쁘다”는 이야기가 아닙니다. 증거 인덱스에 남은 제품화 구간, 곧 `2026-05-12 4847872`의 async Cloud Drop, `b6f3ea8`의 pricing page, `2e4593d`의 PayPal entitlement, `2026-05-14 a004c91`의 Free plan cloud policy, `212d751`의 gated account and billing surface 비활성화라는 흐름 안에서만 이야기합니다. 핵심은 가격 정책이 제품 구조를 얼마나 빨리 바꾸는가입니다.

🧭 rollback은 왜 판단의 흔적이 되었나

Cloud Drop 이전의 PonsWarp는 어렵지만 비교적 단순한 약속을 했습니다. sender와 receiver가 같은 시간에 들어오고, WebRTC 연결이 붙고, 파일이 깨지지 않고, receiver가 저장 완료를 확인하면 전송이 끝납니다. 이 흐름은 이미 충분히 복잡했습니다. STUN/TURN, signaling, backpressure, 저장 완료 handshake, ZIP64, reordering buffer, file signature까지 여러 층이 필요했습니다.

Cloud Drop은 이 약속을 바꿉니다. receiver가 지금 없어도 됩니다. sender가 업로드를 끝내면 서버 쪽 저장소가 일정 시간 파일을 들고 있고, receiver는 나중에 내려받습니다. 사용자 관점에서는 편해집니다. 하지만 제품 관점에서는 “누가 언제까지 무엇을 책임지는가”가 완전히 달라집니다.

여기서 무료 정책이 붙으면 책임은 더 또렷해집니다. 무료 10GB / 24시간은 마케팅 문구처럼 보이지만 실제로는 저장 비용, abuse 방지, 업로드 재개, 다운로드 실패, 모바일 복귀, 만료 처리, 지원 문의의 범위를 정합니다. 이 숫자를 공개 UI에 올리는 순간 제품은 그만큼의 운영 체력을 갖춘 것처럼 보입니다. rollback은 그 착시를 늦게라도 걷어 낸 조치였습니다.

🧱 당시 제품 상태: 기능은 붙었지만 약속은 아직 무거웠다

제품화 구간의 커밋들은 속도가 빠릅니다. `4847872`는 지연 다운로드를 위한 async Cloud Drop을 열었습니다. 사용자가 동시에 온라인이어야 한다는 P2P의 제약을 줄이는 방향입니다. `b6f3ea8`은 Cloud Drop pricing page를 first-class로 추가했습니다. `f8f2120`과 `2e4593d`는 Stripe Checkout에서 PayPal로 이어지는 entitlement 흐름을 만들었습니다. `3628858`은 대용량 Cloud Drop 업로드를 resumable multipart uploads로 바꿨습니다. 그리고 `a004c91`은 Free plan을 first-class cloud policy로 노출했습니다.

이 흐름만 보면 제품이 빠르게 성숙해지는 것처럼 보입니다. 기능, 가격, 결제, 권한, 무료 플랜이 한 줄로 이어지기 때문입니다. 하지만 같은 줄 안에는 서로 다른 종류의 책임이 섞여 있습니다. Cloud Drop은 전송 플로우의 확장이고, pricing page는 구매 판단의 표면이고, entitlement는 계정/권한 시스템이며, resumable upload는 실패 복구 구조입니다. Free plan은 이 모든 것을 사용자에게 하나의 약속으로 묶어 버립니다.

그래서 `212d751 Disable gated account and billing surfaces`가 중요합니다. 이 커밋은 단순히 결제 버튼을 숨긴 사건이 아닙니다. 제품이 아직 “가격표가 있는 서비스”처럼 행동하기보다, 먼저 전송과 Cloud Drop의 신뢰 조건을 더 확인해야 한다는 판단을 보여 줍니다. rollback은 후퇴이지만, 아무 생각 없는 후퇴는 아니었습니다.

⚙️ 시스템 구조로 보면 무엇이 되돌아갔나

무료 플랜 rollback을 UI 변경으로만 보면 핵심을 놓칩니다. PonsWarp의 구조에서 free / paid 정책은 네 층을 건드립니다.

첫째, Product and UI 층입니다. SenderView와 CloudSenderView가 사용자에게 어떤 선택지를 보여 주는지가 바뀝니다. “바로 보내기”와 “Cloud Drop으로 맡기기” 사이에 가격과 계정 문구가 끼어들면 사용자는 전송 도구를 쓰는 것이 아니라 서비스 플랜을 고르는 상태가 됩니다.

둘째, Browser transfer engine 층입니다. 직접 전송은 WebRTC DataChannel, worker, backpressure, receiver 저장 완료의 문제입니다. Cloud Drop은 upload session, chunked upload, retry, server-side object lifecycle 쪽으로 무게가 이동합니다. 무료 제한이 있으면 엔진은 단순히 파일을 보내는 것이 아니라 정책에 맞는 크기와 기간과 권한을 확인해야 합니다.

셋째, Storage and recovery 층입니다. post-21과 post-22에서 다룬 partial recovery와 완료 판단은 Cloud Drop에서도 사라지지 않습니다. 오히려 receiver가 나중에 돌아오는 흐름에서는 “업로드가 끝났다”와 “다운로드가 안전하게 끝났다”를 더 분리해야 합니다.

넷째, Core and backend 층입니다. signaling 서버는 매치메이커에서 room cleanup, readiness, TURN, billing, auth, database 쪽으로 이미 무거워지고 있었습니다. 여기에 entitlement가 붙으면 백엔드는 파일 전달의 보조 장치가 아니라 상품 접근권을 판정하는 control plane이 됩니다. rollback은 이 control plane을 없앤 것이 아니라, 너무 이른 시점에 제품 표면으로 올리는 일을 멈춘 것입니다.

🚧 실제 실패 지점: 가격보다 신뢰가 먼저였다

무료 플랜을 공개하면 사용자는 제한을 기억합니다. 10GB까지 되는구나. 24시간은 보관되는구나. 계정이 있으면 더 큰 파일이나 더 긴 보관이 되겠구나. 이 기억은 구현 상세를 기다려 주지 않습니다. 실패가 나면 “베타라서”가 아니라 “약속이 깨졌다”가 됩니다.

PonsWarp는 이미 신뢰 문제에 오래 붙잡혀 있었습니다. `21dc9ba`의 저장 완료 handshake는 sender 화면의 완료와 receiver 저장 완료가 다르다는 사실에서 나왔습니다. `4650d02`의 파일 깨짐 문제 해결은 대용량 전송에서 무결성이 UX보다 먼저라는 교훈을 남겼습니다. `54cf5f4`의 receiver-side backpressure는 속도를 밀어붙이는 것보다 저장 경계를 존중해야 한다는 판단이었습니다. 이런 기록을 지나온 제품이 Cloud Drop에서 다시 “무료 정책”을 먼저 강하게 노출하면 같은 실수를 다른 층에서 반복할 위험이 있었습니다.

그 위험은 돈 때문만이 아닙니다. 무료 사용자는 비용을 내지 않아도 제품 신뢰를 평가합니다. 유료 사용자는 더 엄격하게 평가합니다. 운영자는 abuse와 저장 비용을 봅니다. 개발자는 entitlement와 recovery와 만료 처리의 엣지를 봅니다. Free plan rollback은 이 네 관점이 아직 한 화면에서 자연스럽게 만날 준비가 덜 됐다는 신호였습니다.

🔄 설계 변경: 팔기 전에 덜 약속하기

rollback 이후의 더 나은 질문은 “어떻게 유료화할까”가 아니라 “무엇을 제품 약속으로 내걸 수 있는가”였습니다. 이 질문은 작지만 중요합니다.

Cloud Drop 자체는 필요했습니다. 사용자가 동시에 온라인이어야 한다는 직접 전송의 제약은 실제 제품 플로우에서 큽니다. `4847872`가 열어 둔 async Cloud Drop 방향은 그 문제를 정면으로 다룹니다. `3628858`의 resumable multipart uploads도 대용량 업로드 실패를 현실적인 문제로 본 결과입니다. 그러므로 rollback은 Cloud Drop을 부정한 것이 아닙니다.

되돌린 것은 순서였습니다. 먼저 가격표와 계정 문구를 세우고 그 뒤에 신뢰 조건을 맞추는 순서가 아니라, Cloud Drop의 실패 복구와 모바일 복귀와 운영 측정을 더 확인한 뒤 약속의 크기를 정하는 순서입니다. `2026-05-17 8f7299d`의 모바일 receiver backgrounding 복구, `2026-06-08 d88a625`의 GA4 production traffic measurement는 이 관점에서 이어지는 기록으로 읽을 수 있습니다. 팔기 전에 실제 사용 흐름을 더 봐야 했습니다.

⚖️ 지금 돌아보는 판단

지금 돌아보면 free plan rollback은 부끄러운 후퇴라기보다 필요한 제동이었습니다. 제품을 만들다 보면 가격 정책을 붙이는 순간 갑자기 서비스가 된 것 같은 기분이 듭니다. 무료 플랜이 있고, 유료 플랜이 있고, entitlement가 있으면 구조가 완성된 것처럼 보입니다. 하지만 파일 전송 제품에서 구조의 완성은 가격표가 아니라 실패한 전송을 얼마나 정직하게 다루는가에 있습니다.

PonsWarp는 이미 여러 번 이 사실을 배웠습니다. 완료 표시는 저장 완료 이후여야 했고, 빠른 전송보다 무결성이 먼저였고, 서버 없는 전송이라는 말은 절반만 맞았습니다. free plan rollback은 같은 교훈이 제품화와 돈의 문제에서 다시 나타난 장면입니다. 제품이 감당할 수 있는 책임보다 먼저 약속을 걸면, 그 약속은 성장 장치가 아니라 부채가 됩니다.

그래서 이 판단은 소극적인 결정이 아니었습니다. 오히려 제품 표면을 줄여서 신뢰 조건을 다시 앞에 세운 결정이었습니다. Cloud Drop을 계속 실험하되, 무료/유료의 언어가 사용자의 기대를 과하게 끌어올리는 것을 막았습니다. 그 덕분에 이후의 질문은 더 현실적으로 바뀝니다. “얼마를 받을까”보다 “어떤 실패까지 책임질 수 있을까”가 먼저 오게 됩니다.
