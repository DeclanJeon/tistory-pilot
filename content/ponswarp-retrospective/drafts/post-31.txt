PonsWarp를 처음 설명할 때 가장 매력적인 문장은 “서버에 파일을 올리지 않고 브라우저끼리 보낸다”였습니다.

이 문장은 틀리지 않습니다. WebRTC DataChannel이 직접 경로를 얻고, sender와 receiver가 동시에 살아 있고, 브라우저 저장 흐름이 끝까지 버티면 파일 바이트는 앱 서버의 저장소를 거치지 않습니다.

하지만 이 문장을 “서버가 필요 없는 제품”으로 읽으면 그때부터 틀립니다. PonsWarp는 파일 저장 서버를 피하려 했지, 서버 책임 자체를 없앤 서비스가 아니었습니다.

[PonsWarp serverless transfer is half true]

파일 바이트는 직접 흐를 수 있지만, 연결과 릴레이와 운영 상태는 서버 책임을 남깁니다.

🧭 이 글의 흐름

당시 장면 — 처음 믿었던 문장을 먼저 복원합니다.

실패 지점 — 절반만 맞았던 전제가 어디에서 깨졌는지를 코드와 기록으로 확인합니다.

지금의 판단 — 기술 선택을 제품 책임으로 다시 읽는 기준을 회고의 결론으로 둡니다.

💡 이 글은 P2P라는 말을 부정하려는 글이 아닙니다. PonsWarp에서 “서버 없는 전송”이 어디까지 맞았고, 어디서부터 제품 운영의 말로 바뀌어야 했는지 정리합니다.

🧭 당시 제품 상태: 파일은 직접, 연결은 서버

🎯 독자가 가져갈 질문

이 글은 서버 없는 전송이라는 말의 절반만 맞았던 이유 라는 사건을 기능 소개로 소비하지 않습니다. 절반만 맞았던 전제가 어디에서 깨졌는지를 따라가면서, 왜 그 선택이 코드 변경을 넘어 제품 신뢰의 문제였는지 확인합니다.

초기 제품 표면은 단순했습니다. 보내는 사람은 파일을 고르고 방을 엽니다. 받는 사람은 링크나 코드를 통해 들어오고, 두 브라우저가 연결되면 파일을 받습니다. 이 흐름만 놓고 보면 서버는 잠깐 중매를 서는 존재처럼 보입니다.

그런데 실제 시스템 구조는 두 갈래였습니다. Data plane은 브라우저 사이의 파일 바이트 흐름입니다. chunk가 만들어지고, packet으로 묶이고, WebRTC DataChannel을 지나 receiver worker와 DirectFileWriter 쪽으로 내려갑니다. 반면 control plane은 서버가 맡습니다. 방 생성, peer 매칭, offer/answer, ICE candidate, TURN credential, cleanup 같은 흐름입니다.

이 둘을 섞어 말하면 제품 설명이 편해집니다. 하지만 장애를 만났을 때는 반드시 나눠야 했습니다. 파일 바이트가 서버 저장소를 거치지 않는다는 사실은 control plane 장애를 없애 주지 않습니다.

🧱 서버가 정말로 하던 일

PonsWarp의 반복 구조에서 서버는 처음부터 완전히 사라진 적이 없었습니다. PonsWarp/src/services/signaling-adapter.ts 와 WebRTC 연결 흐름은 브라우저가 혼자 상대를 발견하지 않는다는 사실을 전제로 합니다. 방 상태와 signaling 메시지는 어딘가에서 오가야 합니다.

모바일은 이 경계를 더 세게 드러냈습니다. 2025년 11월 20일의 4efb394 는 모든 호스트 허용과 추가 STUN 서버 적용으로 연결 후보를 넓히는 방향이었습니다. 다음 날 2def330 은 TURN 서버 설정을 동적으로 가져와 모바일 WebRTC 연결을 안정화하는 쪽으로 움직였습니다.

이후 2025년 12월 10일 44fb5ad 로 ponswarp-signaling-rs 가 시작되고, 12월 11일 b834716 에서 signaling 서버 안정성과 배포 자동화가 붙습니다. 2026년 5월 17일 f1c69cb 는 signaling room cleanup deadlock 방어를 다룹니다. 서버가 “잠깐 메시지만 전달하는 얇은 것”으로 남지 않았다는 증거입니다.

[PonsWarp control plane and data plane split]

파일 데이터 경로와 연결 제어 경로를 나눠야 “서버 없는” 말의 범위가 정확해집니다.

⚙️ Control plane과 data plane을 나눠야 했다

PonsWarp에서 서버 없는 전송이라는 말이 절반만 맞았던 이유는 이 분리에서 나옵니다. 파일 데이터의 기본 경로만 보면 서버 없는 쪽에 가깝습니다. 파일이 서비스 운영자의 디스크에 업로드되어 보관되지 않는다는 점은 분명한 제품 가치입니다.

하지만 연결 제어는 서버 없는 구조가 아니었습니다. WebRTC는 양쪽 브라우저가 갑자기 서로를 알아보는 기술이 아닙니다. offer와 answer가 오가야 하고, ICE candidate가 교환되어야 하며, 네트워크가 직접 경로를 허용하지 않으면 TURN relay 후보가 필요합니다.

더 정확한 설명은 “파일 저장은 기본적으로 클라이언트 간에 처리하고, 연결 제어와 운영 상태는 서버가 맡는 전송 서비스”에 가깝습니다.

🚧 실패 지점: 서버가 얇다고 믿으면 운영도 얇아 보인다

처음에는 signaling 서버를 얇게 생각하기 쉽습니다. 파일을 저장하지 않으니 데이터베이스도 작고, 처리량도 별것 아니고, 장애가 나도 새로고침하면 되지 않겠느냐고 생각하게 됩니다. 하지만 파일 전송 제품에서 연결 실패는 사소한 에러가 아닙니다.

TURN은 이 착각을 깨는 대표적인 지점이었습니다. TURN이 개입하면 데이터가 relay 서버를 지나갈 수 있고, 그 순간 대역폭 비용과 credential 발급, TTL, fallback URL, 보안 설정이 운영 문제가 됩니다. 서버에 파일을 저장하지 않는다고 해서 서버 트래픽 비용이 0이 되는 것도 아닙니다.

cleanup도 마찬가지입니다. 방이 사라져야 할 때 사라지지 않거나, 정리 과정에서 deadlock이 생기면 사용자는 내부 상태를 모릅니다. 그냥 다음 연결이 이상해지거나, 대기 화면이 풀리지 않거나, 누군가 들어왔는데 진행되지 않는다고 느낍니다.

[PonsWarp backend responsibility growth]

서버 책임은 signaling 중매에서 TURN, cleanup, readiness, Cloud Drop 같은 운영 책임으로 커졌습니다.

🔄 Cloud Drop은 P2P의 배신이 아니라 조건의 인정이었다

서버 책임이 커진 흐름은 나중에 Cloud Drop으로 더 선명해졌습니다. 2026년 5월 12일 4847872 는 delayed downloads를 위한 async cloud drops를 켭니다. 같은 날 가격 페이지, entitlement, 결제 흐름이 이어지고, 2026년 5월 14일 3628858 은 대용량 Cloud Drop 업로드를 part 단위로 재개 가능하게 만듭니다.

이것을 “P2P를 하다가 서버 업로드로 도망갔다”고만 보면 흐름을 놓칩니다. 더 정확히는 direct transfer가 성립하는 조건과 성립하지 않는 조건을 제품이 분리하기 시작한 것입니다.

“항상 서버가 없다”가 아니라 “가능한 경우 파일 저장 서버 없이 직접 보내고, 그렇지 않은 경우에는 relay나 cloud delivery를 제품 플로우로 인정한다”에 가까워졌습니다.

📐 지금 돌아보는 설계 기준

지금 돌아보면 PonsWarp의 실수는 서버를 쓴 것 자체가 아니었습니다. 더 위험한 실수는 서버가 얇으니 제품 책임도 얇을 것이라고 생각한 부분이었습니다. P2P 제품은 서버 비용을 줄일 수 있지만, 서버 운영을 없애지는 않습니다.

그래서 좋은 설명은 기술 자랑보다 경계 설명이어야 했습니다. “파일은 기본적으로 브라우저끼리 흐릅니다” 다음에 “하지만 연결을 붙이고, 모바일 NAT를 우회하고, 실패한 방을 정리하고, 비동기 전달을 제공하는 서버 책임이 있습니다”를 같이 말해야 했습니다.

React 화면은 sender, receiver, CloudSenderView처럼 사용자 플로우를 나눕니다. 브라우저 전송 엔진은 WebRTC, worker, backpressure, writer 완료 신호를 닫습니다. Rust/WASM 코어는 packet, ZIP64, crypto, reordering 같은 바이트 계약을 맡습니다. 그리고 signaling backend는 방과 연결, TURN, 운영 상태를 책임집니다.

🧭 지금 남는 판단

“서버 없는 전송”은 PonsWarp의 중요한 출발점이었습니다. 파일을 중앙 서버에 올리지 않고 직접 보내고 싶다는 욕망이 없었다면 WebRTC, backpressure, WASM core, integrity check 같은 긴 흐름도 나오기 어려웠습니다.

하지만 제품으로 만들수록 그 문장은 좁아져야 했습니다. 서버 없는 것은 파일 저장 경로의 기본값이지, 연결 제어와 운영 책임의 부재가 아니었습니다. PonsWarp가 배운 것은 서버를 피하는 법이 아니라, 서버가 없어도 되는 책임과 반드시 있어야 하는 책임을 나누는 법에 가까웠습니다.

📝 회고로 다시 쓴 기준

이 포스팅의 중심은 “무엇을 구현했는가”가 아니라 “왜 그 구현이 필요해졌는가”입니다. 그래서 마지막 판단은 기술 선택을 제품 책임으로 다시 읽는 기준을 둡니다. 독자가 세부 API를 몰라도, 당시 제품이 어떤 압력 때문에 그 구조로 이동했는지 따라올 수 있어야 합니다.
