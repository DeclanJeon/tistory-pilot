무료 10GB / 24시간이라는 타협

Cloud Drop을 붙이면 PonsWarp의 문제는 한 가지가 줄어드는 것처럼 보였습니다. 보내는 사람과 받는 사람이 동시에 온라인일 필요가 없어지기 때문입니다. 직접 전송은 링크를 열고, 연결하고, 브라우저가 살아 있고, 네트워크가 버텨야 합니다. Cloud Drop은 일단 서버 쪽에 올려 두고 나중에 받게 만들 수 있습니다. 사용자 입장에서는 훨씬 편한 말입니다.

하지만 제품을 만드는 입장에서는 그 순간 질문이 바뀝니다. “어떻게 직접 보낼 것인가”에서 “얼마나 보관해 줄 것인가”로 넘어갑니다. 무료로 어디까지 허용할지, 보관 시간은 얼마나 줄지, 대용량 파일의 저장 비용과 남용 가능성은 어떻게 막을지, 유료 정책과 어디서 갈라질지 정해야 합니다. 그래서 무료 10GB / 24시간은 단순한 마케팅 문구가 아니라 PonsWarp가 제품으로 버티기 위해 세운 제한선이었습니다.

💡 이 글은 무료 정책이 좋았는지 나빴는지를 판정하려는 글이 아닙니다. `4847872`의 async Cloud Drop, `b6f3ea8`의 pricing page, `3628858`의 resumable multipart upload, `a004c91`의 Free plan 정책, `212d751`의 gated account/billing surface 비활성화 흐름을 기준으로, 왜 무료 10GB / 24시간이 기술·운영·수익화 사이의 타협이 되었는지를 정리합니다.

🧭 당시 제품 상태: 직접 전송만으로는 닫히지 않았다

PonsWarp의 출발점은 브라우저끼리 직접 파일을 보내는 경험이었습니다. React/Vite 기반 제품 표면에서는 `SenderView.tsx`와 `ReceiverView.tsx`가 송신자와 수신자의 상태를 나눠 보여줬고, 아래에서는 `simple-peer` 기반 WebRTC, sender/receiver worker, `DirectFileWriter`, `pons-core-wasm`, signaling backend가 전송을 닫았습니다.

이 구조는 “서버 없는 전송”처럼 설명하기 좋았지만 실제로는 서버를 완전히 피하지 못했습니다. signaling이 필요했고, TURN이 필요했고, 모바일 네트워크와 브라우저 저장 경계를 다뤄야 했습니다. `2def330`이 TURN 서버 설정을 동적으로 가져오게 만든 것도, `21dc9ba`가 전송 완료 후 수신자 저장까지 기다리는 핸드셰이크를 붙인 것도 같은 이유였습니다. 화면에서 전송률이 올라가는 것만으로는 제품 신뢰가 닫히지 않았습니다.

Cloud Drop은 이 압력을 다른 방식으로 푸는 선택이었습니다. 상대가 지금 온라인이 아니어도 됩니다. 수신자가 링크를 나중에 열어도 됩니다. 직접 연결이 실패한 상황에서도 “그럼 클라우드로 맡겨 두자”는 우회로가 생깁니다. 그래서 `4847872`의 delayed downloads용 async Cloud Drop은 단순 기능 추가가 아니라 제품 흐름의 방향을 바꾸는 커밋이었습니다.

☁️ Cloud Drop이 바꾼 사용자 플로우

직접 전송의 사용자 플로우는 비교적 단단합니다. 보내는 사람이 파일을 고르고 링크를 열어 둡니다. 받는 사람이 들어옵니다. 연결이 붙고, 청크가 흐르고, 수신 저장이 끝나야 합니다. 실패하면 둘 중 한쪽이 다시 시도해야 합니다. 이 흐름에서는 서버가 주로 매치메이커와 보조 인프라에 가깝습니다.

Cloud Drop의 플로우는 다릅니다. 보내는 사람은 파일을 업로드합니다. 서버 또는 스토리지 계층은 그 파일을 일정 시간 보관합니다. 링크는 전달되고, 받는 사람은 나중에 다운로드합니다. 여기서는 업로드 완료와 다운로드 완료 사이에 시간이 생깁니다. 그 시간 동안 제품은 파일을 보관하고, 만료시키고, 남용을 막고, 사용자가 “아직 받을 수 있다”고 믿게 만들어야 합니다.

무료 10GB / 24시간은 바로 이 시간의 제품 언어였습니다. 10GB는 “큰 파일도 한 번 써볼 수 있다”는 신호였습니다. 동시에 무제한 보관을 약속하지 않겠다는 비용 경계였습니다. 24시간은 “나중에 받기”를 허용하되, 영구 저장 서비스가 아니라고 선을 긋는 장치였습니다. 이 둘을 합치면 Cloud Drop은 드라이브 서비스가 아니라 임시 전송 보조 기능으로 남을 수 있었습니다.

🧱 시스템 구조: 숫자 하나가 여러 계층을 건드렸다

무료 정책은 UI 문구만 바꾸는 일이 아니었습니다. 제품 표면에서는 사용자가 무료로 가능한 범위를 이해해야 합니다. Cloud Drop 화면은 직접 전송과 다른 기대를 줘야 하고, 10GB와 24시간 제한이 실패 메시지나 업그레이드 유도와 충돌하지 않아야 합니다.

브라우저 전송 엔진 쪽에서는 업로드가 안정적으로 끝나야 했습니다. 직접 전송에서는 peer 연결과 저장 writer가 핵심이었다면, Cloud Drop에서는 업로드 세션, 파트 단위 재시도, 완료 확정이 중요해집니다. `3628858`의 large uploads resumable by parts는 이 경계를 보여줍니다. 10GB를 무료로 허용하려면, 10GB 업로드가 중간 네트워크 흔들림 한 번에 통째로 날아가서는 안 됩니다.

백엔드와 운영 계층은 더 무거워집니다. `ponswarp-signaling-rs`는 이미 auth, billing, database, handlers, protocol, state, `/health`, `/ready`, `/ws` 같은 책임을 갖는 쪽으로 커졌습니다. Cloud Drop이 붙으면 signaling만의 문제가 아니라 저장, 권한, 만료, cleanup, 결제 정책이 함께 들어옵니다. 무료 24시간이라는 문장은 실제로는 TTL, cleanup, abuse limit, readiness를 요구하는 운영 계약입니다.

💸 실제 실패 지점: 무료는 공짜가 아니었다

무료 10GB / 24시간은 사용자에게는 관대해 보이는 조건입니다. 하지만 서비스 운영 관점에서는 공짜가 아닙니다. 누군가가 파일을 올리면 저장 공간을 차지하고, 누군가가 내려받으면 트래픽이 발생합니다. 파일이 크고 보관 시간이 길수록 비용과 남용 가능성은 커집니다. 반대로 제한이 너무 좁으면 Cloud Drop을 붙인 이유가 약해집니다.

여기서 PonsWarp의 어려움은 기술보다 제품 설명에 가까웠습니다. 직접 전송은 “브라우저끼리 보낸다”는 말로 설명할 수 있었습니다. Cloud Drop은 “서버에 임시로 맡긴다”는 말이 필요합니다. 무료 10GB / 24시간은 그 말을 가능하게 하는 숫자였지만, 동시에 유료 정책을 예고합니다. 무료에서 충분히 써볼 수 있어야 하지만, 더 큰 파일이나 더 긴 보관은 유료로 넘어가야 합니다.

그래서 `b6f3ea8`의 Cloud Drop pricing page와 `f8f2120`, `2e4593d`의 checkout/billing 흐름은 자연스럽게 이어집니다. 가격표가 생긴다는 것은 단지 결제 버튼이 생긴다는 뜻이 아닙니다. 무료와 유료의 차이를 설명해야 하고, 결제 후 entitlement를 어떻게 부여할지 정해야 하며, 실패했을 때 사용자가 어느 권리를 가진 상태인지 판단해야 합니다.

🔄 설계 변경: 기능에서 정책으로

Cloud Drop 이전의 많은 변경은 “전송이 실제로 안전하게 끝나는가”에 가까웠습니다. 메모리 폭발을 막고, 청크 순서를 바로잡고, backpressure를 걸고, RTT 기반으로 속도를 조절하고, WASM ZIP64와 재정렬 버퍼를 붙이는 일은 모두 바이트 흐름의 신뢰를 높이는 쪽이었습니다.

무료 10GB / 24시간은 다른 종류의 설계 변경이었습니다. 이제 제품은 바이트만 다루지 않습니다. 시간과 권리를 다룹니다. 언제까지 받을 수 있는지, 누가 어느 크기까지 올릴 수 있는지, 무료 사용자가 어디서 멈추는지, 유료 사용자는 무엇을 더 받는지를 다룹니다. 이 변화는 코드 구조에서도 CloudSenderView, backend policy, billing/entitlement, resumable upload가 한 흐름 안에 묶여야 함을 뜻했습니다.

흥미로운 지점은 `a004c91`과 `212d751`입니다. 하나는 Free plan을 first-class cloud policy로 드러낸 흐름이고, 다른 하나는 gated account와 billing surface를 비활성화한 흐름입니다. 이 둘을 같이 보면 정책이 단번에 고정되지 않았다는 사실이 보입니다. 무료 정책을 제품의 중심으로 세우려 했지만, 계정과 결제를 전면에 세우는 순간 진입 장벽이 생깁니다. PonsWarp는 이 경계에서 계속 흔들렸습니다.

📐 제품 판단: 10GB와 24시간이 하려던 일

10GB는 작지 않은 숫자입니다. 이미지 몇 장을 보내는 서비스가 아니라, 동영상·압축 파일·작업 결과물 같은 큰 파일 전송까지 염두에 둔 숫자입니다. 이 숫자가 없으면 Cloud Drop은 PonsWarp의 대용량 전송 정체성과 어긋납니다. 하지만 무제한에 가까워지면 제품은 임시 전송이 아니라 무료 스토리지처럼 오해됩니다.

24시간도 비슷합니다. 너무 짧으면 “나중에 받기”라는 Cloud Drop의 장점이 사라집니다. 너무 길면 보관 서비스가 됩니다. 하루라는 시간은 보내는 사람과 받는 사람이 같은 날 안에 비동기로 움직일 수 있게 하면서도, 서비스가 영구 보관 책임을 지지 않는 선입니다.

따라서 이 정책은 사용자 친절과 운영 방어 사이의 중간값이었습니다. P2P가 실패하거나 시간이 맞지 않을 때 도망갈 길을 주되, PonsWarp가 Dropbox나 Google Drive 같은 장기 저장 제품으로 착각되지 않게 막는 장치였습니다. 이 판단은 깔끔하지만, 실행은 전혀 깔끔하지 않았습니다. 정책을 화면에 쓰는 순간부터 가격표, 만료 안내, 업로드 실패 복구, 모바일 수신 재개, cleanup, analytics까지 모두 따라옵니다.

🧭 지금 돌아보는 판단

지금 돌아보면 무료 10GB / 24시간은 꽤 정직한 타협이었습니다. 직접 전송만으로는 사용자 상황을 다 받기 어려웠고, Cloud Drop을 무제한에 가깝게 열 수는 없었습니다. 큰 파일 전송 제품이라는 정체성을 지키려면 무료 용량은 너무 작아서는 안 됐고, 운영 가능한 서비스가 되려면 보관 시간은 반드시 닫혀 있어야 했습니다.

다만 이 타협은 제품의 복잡도를 줄이지는 못했습니다. 오히려 복잡도를 다른 층으로 옮겼습니다. WebRTC의 연결 문제를 일부 피하는 대신, 저장 비용과 만료 정책과 결제 권한과 사용자 안내 문제가 들어왔습니다. 그래서 Cloud Drop은 PonsWarp를 더 실용적으로 만들었지만, 동시에 “우리는 무엇을 파는 제품인가”라는 질문을 더 세게 만들었습니다.

PonsWarp가 더 오래 살아남으려면 이 정책이 더 일찍 제품의 중심 언어가 되었어야 합니다. 직접 전송이 기본이고 Cloud Drop은 예외인지, Cloud Drop이 중심 상품이고 P2P는 빠른 무료 경로인지, 무료 10GB / 24시간이 acquisition 장치인지 운영 방어선인지가 더 빨리 닫혀야 했습니다. 숫자는 있었지만, 그 숫자가 제품의 우선순위를 완전히 닫지는 못했습니다.
