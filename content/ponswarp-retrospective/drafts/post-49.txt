PonsWarp가 PonsLink 계열로 이어진 방식

PonsWarp를 한 문장으로만 기억하면 “브라우저에서 대용량 파일을 직접 보내려던 프로젝트”가 됩니다. 틀린 말은 아니지만, 그 설명만으로는 뒤에 나온 PonsLink 계열을 이해하기 어렵습니다. PonsWarp가 남긴 것은 파일 전송 기능 하나가 아니라, 브라우저 안에서 실시간 상태를 믿을 수 있게 만드는 방법에 가까웠습니다.

PonsLink는 다른 제품입니다. 회의방, public desk, request status, lounge, session access, PonsCast 같은 흐름이 있고, 파일 하나를 보내는 화면보다 더 넓은 실시간 협업 표면을 다룹니다. 그런데 코드를 읽는 방식은 낯설지 않습니다. WebRTC 협상은 순서가 깨질 수 있고, DataChannel은 막힐 수 있고, 사용자는 잠깐 나갔다 돌아올 수 있으며, 서버는 미디어를 대신 운반하지 않더라도 권한과 상태를 책임져야 합니다. 이 문장들은 PonsWarp 회고에서 이미 여러 번 나왔던 문장입니다.

💡 이 글은 PonsLink가 PonsWarp의 단순 후속 버전이라고 말하지 않습니다. 이름이 이어졌다고 같은 제품이라는 뜻은 아닙니다. 근거는 이 디렉터리의 series-plan, evidence-index, 그리고 이미 작성된 PonsLink 알고리즘/딥다이브 원고에 남은 범위로 제한합니다. 핵심은 PonsWarp에서 반복해서 부딪힌 “브라우저 실시간 제품의 신뢰 경계”가 PonsLink에서 더 넓은 제품 구조로 확장됐다는 점입니다.

🧭 문제 제기: 파일 전송 문제는 왜 회의방 문제로 번졌나

PonsWarp의 출발점은 직접적이었습니다. sender가 파일을 고르고, receiver가 링크로 들어오고, WebRTC DataChannel로 chunk를 받습니다. 처음에는 이 흐름이 파일 전송 제품의 전부처럼 보입니다. 하지만 실제로는 전송보다 주변 상태가 더 많이 문제를 만듭니다. 방이 유지되는가, 상대가 아직 살아 있는가, TURN이 필요한가, receiver가 저장을 끝냈는가, 완료 표시를 언제 믿어도 되는가.

이 질문은 파일 전송에만 갇혀 있지 않습니다. PonsLink의 회의방에서도 같은 일이 벌어집니다. offer와 answer가 동시에 움직이고, ICE candidate가 remote description보다 먼저 도착하고, reconnect 뒤 늦은 메시지가 섞입니다. PonsCast처럼 DataChannel로 미디어 프레임을 보내면 backpressure와 jitter buffer가 다시 나타납니다. request-first 흐름에서는 내부 상태가 더 많아져서, booking status와 reservation status와 session access를 사용자가 이해할 한 문장으로 접어야 합니다.

그래서 PonsWarp에서 PonsLink로 이어진 것은 기능 목록이 아닙니다. “브라우저가 제공하는 이벤트 순서를 그대로 믿지 않는다”, “DataChannel에 넣었다고 사용자에게 끝났다고 말하지 않는다”, “서버가 미디어를 운반하지 않아도 제품 신뢰의 제어면은 맡아야 한다”는 습관입니다.

🧱 당시 제품 상태: PonsWarp는 이미 작은 실시간 시스템이었다

PonsWarp는 파일 전송 앱처럼 보였지만, 2025년 11월 말부터 12월 초의 기록을 따라가면 이미 작은 실시간 시스템에 가까웠습니다. `638bc83`의 대용량 다운로드 메모리 폭발 방지, `21dc9ba`의 수신자 저장 완료 대기 handshake, `2def330`의 TURN 동적 설정, `54cf5f4`의 receiver-side backpressure, `09161ce`의 RTT 기반 동적 혼잡 제어는 모두 같은 방향으로 쌓였습니다.

그 뒤 `15aef19`에서 `pons-core-wasm`이 생기고, ZIP64, reordering buffer, Merkle tree, file signature, zero-copy pool이 이어졌습니다. `44fb5ad`에서는 Rust 기반 signaling 서버가 분리됐고, 2026년 5월에는 Cloud Drop, entitlement, resumable multipart upload, mobile resume, GA4 측정까지 제품화 구간이 붙었습니다.

이 흐름을 보면 PonsWarp는 “빠르게 보내기”에서 끝나지 않았습니다. 사용자의 흐름은 단순했지만 내부는 product/UI, browser transfer engine, storage/recovery, core/backend 네 층으로 나뉘었습니다. 이 네 층 구조가 PonsLink에서 그대로 복제됐다고 말할 수는 없습니다. 하지만 브라우저 제품 표면과 실시간 transport, 저장·복구 또는 상태 지속성, backend control plane을 나눠 보는 관점은 확실히 남았습니다.

⚙️ 시스템 구조: PonsLink는 파일 전송 엔진을 제품 제어면으로 넓혔다

PonsLink 딥다이브 원고는 루트 구조를 `ponslink-room-frontend`와 `ponslink-api-infra`로 나눠 읽습니다. 프론트엔드는 단순한 방 화면이 아니라 `/public-desk/:identifier`, `/request-status/:token`, `/request-actions/:token/review`, `/session-access/:reservationId`, `/lounge/requests`, `/room/:roomTitle` 같은 route family를 품습니다. 방은 시작점일 수도 있지만, 어떤 경우에는 요청과 승인과 입장 가능 시간 뒤에 열리는 마지막 지점이 됩니다.

백엔드는 미디어 서버라기보다 control plane에 가깝습니다. room/session token을 발급하고, TURN credential을 만들고, signaling을 검증하고, 결제와 예약 같은 side effect를 다룹니다. 이 구조는 PonsWarp의 Rust signaling 서버와 Cloud Drop 제품화 구간에서 이미 보였던 전환과 닮았습니다. 서버 없는 P2P라는 말은 절반만 맞고, 사용자가 믿을 수 있는 제품이 되려면 서버는 권한, 상태, 복구, 운영 경계를 맡아야 합니다.

PonsLink 알고리즘 글에서도 같은 패턴이 반복됩니다. 협상 상태 머신은 `makingOffer`, `negotiationQueued`, `polite`, `ignoreOffer`, `remoteDescriptionRevision`, `pendingCandidates` 같은 값을 묶어 offer collision과 stale candidate를 다룹니다. realtime queue는 latest-wins와 reliable queue를 나눕니다. 파일 전송은 sender worker의 congestion window와 receiver worker의 OPFS 조립으로 움직입니다. replay와 idempotency는 reconnect 후 놓친 이벤트와 중복 mutation을 분리합니다.

🚧 실제 실패 지점: 재사용된 것은 코드보다 경계 감각이었다

여기서 조심해야 할 점이 있습니다. PonsWarp의 코드를 그대로 PonsLink에 옮겼다고 말하면 근거가 약해집니다. PonsLink 자료에는 PonsLink만의 파일 sender worker, room orchestrator, signaling broker, request state model, PonsCast protocol이 등장합니다. 이것들은 새 제품의 문맥에서 다시 설계된 코드입니다.

하지만 실패의 모양은 이어집니다. PonsWarp에서 DataChannel queue를 그대로 믿었다가 receiver 저장 완료 handshake가 필요해졌듯, PonsLink에서도 DataChannel은 메시지 생존 등급과 backpressure 정책을 필요로 합니다. PonsWarp에서 chunk 순서 역전과 buffer 관리가 파일 손상을 만들었듯, PonsLink 파일 전송도 sequencer와 out-of-order pending chunks를 둡니다. PonsWarp에서 TURN과 signaling cleanup이 운영 문제가 됐듯, PonsLink도 TURN credential, rate limit, replay store, session access 같은 backend 경계를 갖습니다.

그러니 계보는 “코드 재사용”보다 “실패 분류법의 재사용”에 가깝습니다. 무엇이 transport 문제인지, 무엇이 UX 상태 문제인지, 무엇이 서버 제어면 문제인지, 무엇이 운영 준비도 문제인지 나누는 방식입니다.

🔄 설계 변경: room-first가 아니라 request와 상태가 앞에 온다

PonsWarp의 사용자 플로우는 sender와 receiver가 동시에 온라인인 상황을 기본으로 했습니다. Cloud Drop이 붙으면서 이 전제가 흔들렸습니다. 사용자가 항상 동시에 있지 않아도 파일을 전달하고 싶어 했고, 그러면 업로드, 링크, 만료, 요금제, entitlement가 전송 앞에 놓입니다.

PonsLink에서는 이 변화가 더 앞으로 나옵니다. 방에 들어가는 것이 전부가 아니라, public desk에서 요청을 남기고, host가 라운지에서 판단하고, 예약과 입장 권한이 만들어진 뒤에 room으로 들어가는 흐름이 있습니다. 이때 중요한 코드는 미디어 전송 코드만이 아닙니다. request status를 어떻게 접을지, session access를 어떤 HTTP 상태로 돌려줄지, checkout mutation을 어떻게 idempotent하게 만들지, reconnect 뒤 room event를 어떻게 replay할지가 제품의 체감 품질을 정합니다.

이 변화는 PonsWarp의 후반부와 닿아 있습니다. 무료 10GB / 24시간, 결제, entitlement, free plan rollback, analytics 같은 기록은 전송 엔진 밖의 제품 판단이 얼마나 큰 비중을 차지하는지 보여 줍니다. PonsLink는 그 판단을 더 넓은 실시간 협업 제품으로 가져간 셈입니다.

⚖️ 지금 돌아보는 판단

지금 돌아보면 PonsWarp가 PonsLink 계열로 이어진 방식은 기술 브랜드의 연속보다 문제의 연속에 가깝습니다. PonsWarp는 파일 전송이라는 좁은 사용 사례 안에서 브라우저 P2P의 거의 모든 불편한 경계를 만났습니다. NAT traversal, TURN, DataChannel backpressure, 저장 완료, 무결성, 복구, Cloud Drop, 결제, 측정까지 한 번씩 통과했습니다.

PonsLink는 그 경계를 더 넓은 제품으로 펼칩니다. 회의방의 WebRTC negotiation, realtime queue, PonsCast, request-first flow, replay/idempotency, session access는 서로 다른 기능처럼 보이지만 공통 질문은 같습니다. 사용자가 보는 상태가 실제 시스템 상태와 어긋나지 않게 하려면 어디서 기다리고, 어디서 버리고, 어디서 재시도하고, 어디서 서버가 보증해야 하는가.

그래서 PonsWarp의 가장 중요한 유산은 “빠른 파일 전송 엔진”이 아니었다고 봅니다. 더 정확히는 브라우저 실시간 제품에서 거짓 완료, 거짓 연결, 거짓 준비 상태를 줄이려는 태도였습니다. PonsLink 계열은 그 태도를 파일 전송 밖으로 꺼내어 방, 요청, 콘텐츠, 결제, 운영 상태까지 넓힌 결과에 가깝습니다.
