Cloud Drop은 왜 붙었나

PonsWarp가 처음부터 Cloud Drop을 중심 상품으로 설계된 서비스였던 것은 아닙니다. 출발점은 여전히 직접 전송이었습니다. 보내는 사람이 파일을 고르고, 링크를 열고, 받는 사람이 브라우저로 들어오면 WebRTC DataChannel을 통해 파일이 흘러가는 구조였습니다. 이 흐름은 제품 설명으로는 아주 매력적입니다. 서버에 파일을 맡기지 않고, 설치 없이, 링크 하나로 바로 주고받는다는 말은 파일 전송 서비스가 가질 수 있는 가장 깨끗한 문장에 가깝습니다.

그런데 실제 제품은 그 문장만으로 닫히지 않았습니다. 받는 사람이 지금 온라인이 아닐 수 있고, 모바일 브라우저가 백그라운드로 내려갈 수 있고, TURN을 거쳐도 연결이 흔들릴 수 있고, 전송이 끝났다고 표시된 뒤에도 저장 완료를 따로 확인해야 했습니다. Cloud Drop은 이 문제들을 부정하려고 붙은 기능이 아니었습니다. 직접 전송의 장점을 유지하려다 보니, 직접 전송이 감당하지 못하는 시간의 간격을 메우는 장치가 필요해졌습니다.

💡 이 글은 Cloud Drop을 “클라우드 저장소를 붙였다” 정도로 보지 않습니다. PonsWarp가 P2P 파일 전송에서 delayed download, pricing, entitlement, resumable multipart upload로 넘어가며 제품의 언어가 어떻게 바뀌었는지를 정리합니다.

🧭 당시 제품 상태: 직접 전송은 이미 충분히 복잡했다

Cloud Drop이 붙기 전의 PonsWarp도 단순한 실험 앱은 아니었습니다. `src/App.tsx`, `SenderView.tsx`, `ReceiverView.tsx`가 사용자의 송신·수신 흐름을 맡고, 그 아래에서 `simple-peer` 기반 WebRTC, sender/receiver worker, `DirectFileWriter`, `pons-core-wasm`, signaling backend가 같이 움직였습니다. 사용자는 파일 하나를 보내는 것처럼 느끼지만, 내부에서는 연결 성립, 청크 생성, 암호화, 재정렬, 저장, 완료 확인이 모두 맞아야 했습니다.

초기 커밋 기록만 봐도 이 부담은 금방 드러납니다. `638bc83`은 대용량 파일 다운로드 시 메모리 폭발을 막기 위해 들어갔고, `21dc9ba`는 전송 완료 후 수신자 저장까지 기다리는 양방향 핸드셰이크를 붙였습니다. `2def330`은 TURN 서버 설정을 동적으로 가져와 모바일 WebRTC 연결을 안정화하려 했고, `db175bf`와 `4650d02`는 청크 순서, 버퍼 관리, 파일 깨짐 문제를 계속 붙잡은 흔적입니다.

이 흐름에서 중요한 것은 “직접 전송이 실패했다”가 아닙니다. 오히려 직접 전송을 진짜 제품처럼 만들수록 더 많은 경계가 보였습니다. 특히 시간의 경계가 컸습니다. 보내는 사람과 받는 사람이 같은 시간에 같은 흐름 위에 있어야 한다는 조건은 기술적으로는 자연스럽지만, 사용자의 생활에는 자주 맞지 않습니다. 파일을 지금 올려두고, 상대가 나중에 받게 하고 싶다는 요구는 파일 전송 제품에서 피하기 어렵습니다.

☁️ Cloud Drop이 해결하려 한 문제

Cloud Drop의 핵심은 “나중에 받기”였습니다. P2P 직접 전송은 양쪽 브라우저가 동시에 살아 있어야 합니다. 이 조건이 맞으면 서버 저장 비용을 줄이고 빠른 전송 경험을 줄 수 있습니다. 하지만 조건이 깨지는 순간 제품은 사용자에게 설명하기 어려운 실패를 보여줍니다. 상대가 늦게 들어왔거나, 모바일이 잠깐 잠겼거나, 네트워크가 바뀌었다는 이유로 다시 처음부터 시작해야 한다면 사용자는 WebRTC의 사정을 이해해주지 않습니다.

`4847872 Enable async cloud drops for delayed downloads`는 이 지점을 직접 가리킵니다. Cloud Drop은 파일을 임시로 맡겨두고, 수신자가 나중에 받을 수 있게 하는 방향이었습니다. 이 기능은 P2P를 포기하는 선택이라기보다 P2P가 약한 상황을 우회하는 보완책에 가까웠습니다. 직접 전송은 “둘이 지금 만났을 때” 강하고, Cloud Drop은 “둘이 동시에 있지 않을 때” 필요합니다.

하지만 이 보완책은 곧 제품 표면이 됩니다. 파일을 어디에 얼마나 오래 보관할지, 무료 사용자는 어느 정도까지 허용할지, 유료 사용자는 무엇을 더 받는지, 업로드가 중간에 끊기면 어떻게 이어갈지, 다운로드 링크는 언제 만료되는지 같은 질문이 붙습니다. 이 질문들은 전송 엔진 안에서만 풀리지 않습니다. UI, backend, storage, billing, 운영 정책이 함께 답해야 합니다.

🧩 시스템 구조: 기능 하나가 네 층을 모두 건드렸다

PonsWarp의 반복 구조인 네 층으로 보면 Cloud Drop의 성격이 더 분명해집니다.

1층 Product and UI에서는 `CloudSenderView.tsx`가 중요해집니다. 사용자는 더 이상 “상대에게 바로 보내기”만 선택하지 않습니다. Cloud Drop을 선택하고, 업로드 상태를 보고, 링크를 공유하고, 제한과 만료를 이해해야 합니다. 이것은 단순 버튼 추가가 아니라 사용자 플로우의 분기입니다.

2층 Browser transfer engine에서는 직접 WebRTC 전송과 다른 업로드 흐름이 생깁니다. 기존에는 DataChannel, worker, backpressure, 재정렬, 저장 완료 핸드셰이크가 중심이었다면, Cloud Drop에서는 브라우저에서 backend/storage로 큰 파일을 안정적으로 올리는 문제가 중요해집니다. `3628858 Make Cloud Drop large uploads resumable by parts`가 들어온 이유도 여기에 있습니다. 대용량 업로드는 한 번 실패하면 처음부터 다시 올리게 만들 수 없고, 부분 업로드와 재개 가능한 구조가 필요합니다.

3층 Storage and recovery는 더 복잡해집니다. 직접 전송의 저장 경계는 수신자의 브라우저와 로컬 파일 시스템이었습니다. Cloud Drop에서는 임시 object storage와 만료 정책이 들어옵니다. 저장 완료의 의미도 달라집니다. “수신자 디스크에 안전하게 썼다”와 “클라우드에 임시 보관했다”는 서로 다른 약속입니다.

4층 Core and backend에서는 signaling 서버가 단순 매치메이커를 넘어섭니다. `ponswarp-signaling-rs`는 이미 auth, billing, database, handlers, protocol, state, `/health`, `/ready`, `/ws` 같은 운영 표면을 가진 서버로 커지고 있었습니다. Cloud Drop이 붙으면 backend는 업로드 세션, 다운로드 권한, 만료, cleanup, 결제 권한까지 더 직접적으로 다루게 됩니다.

💸 제품화와 돈의 문제가 같이 들어왔다

Cloud Drop이 붙은 뒤 바로 보이는 변화는 수익화 언어입니다. `b6f3ea8 Add a first-class Cloud Drop pricing page`는 Cloud Drop이 단순 내부 기능이 아니라 사용자가 가격표로 이해해야 하는 상품 표면이 되었음을 보여줍니다. `f8f2120 Issue Cloud Drop entitlements from Stripe Checkout`와 `2e4593d Route Cloud Drop billing through PayPal`은 결제 후 권한 부여 흐름까지 들어왔다는 뜻입니다.

이 시점부터 질문은 더 이상 “파일을 잘 보낼 수 있는가”만이 아닙니다. “무료 사용자는 얼마까지 쓸 수 있는가”, “유료 결제 후 어떤 권한이 언제 열리는가”, “권한이 없는 사용자가 큰 파일을 올리려 하면 어디에서 막는가”, “정책을 바꾸면 기존 링크는 어떻게 되는가” 같은 질문이 생깁니다. `a004c91`의 Free plan 정책 노출과 `212d751`의 gated account/billing surface 비활성화는 이 경계가 아직 흔들리고 있었음을 보여줍니다.

이 흔들림은 이상한 일이 아닙니다. Cloud Drop은 기술적으로는 P2P의 약점을 보완하지만, 제품적으로는 저장 비용을 만드는 기능입니다. 저장 비용이 생기면 가격이 필요하고, 가격이 생기면 계정과 권한이 필요하고, 권한이 생기면 결제 실패, 환불, 만료, abuse 대응이 따라옵니다. 파일 전송 문제를 하나 줄이려다 운영 문제가 새로 열린 셈입니다.

🔄 사용자 플로우가 바뀐 지점

직접 전송의 사용자 플로우는 비교적 선명합니다. 보내는 사람이 파일을 고르고 링크를 공유합니다. 받는 사람이 들어오면 연결이 만들어지고, 전송이 진행되고, 저장 완료를 확인합니다. 물론 내부 구현은 어렵지만 사용자에게 설명할 문장은 짧습니다.

Cloud Drop은 문장이 달라집니다. 보내는 사람은 파일을 먼저 업로드합니다. 서비스는 그 파일을 일정 시간 보관합니다. 받는 사람은 나중에 링크를 열어 다운로드합니다. 이때 무료 한도, 보관 시간, 파일 크기, 다운로드 가능 상태가 제품 약속이 됩니다. `무료 10GB / 24시간` 같은 표현이 이후 글의 주제가 되는 것도 이 때문입니다. Cloud Drop은 사용자의 시간을 분리해주는 대신, 제품이 그 사이의 책임을 떠안게 만듭니다.

이 변화는 UX에도 영향을 줍니다. 직접 전송에서는 “상대와 연결 중”, “전송 중”, “저장 중”이 핵심 상태입니다. Cloud Drop에서는 “업로드 준비”, “클라우드 업로드 중”, “링크 생성”, “만료 전 다운로드 가능”, “권한 부족”, “용량 초과”, “재개 가능” 같은 상태가 필요합니다. 상태가 늘면 화면도 늘고, 문구도 늘고, 오류 처리도 늘어납니다.

🧱 실제 실패 지점: 보완 기능이 중심 상품이 되는 순간

Cloud Drop 자체가 잘못된 선택이었다고 보기는 어렵습니다. 오프라인 전달과 delayed download는 파일 전송 서비스에서 현실적인 요구입니다. 직접 전송만으로 모든 사용 상황을 덮겠다는 쪽이 오히려 더 무리일 수 있습니다. 문제는 Cloud Drop을 붙인 순간 PonsWarp가 어떤 서비스인지 더 빨리 정해야 했다는 점입니다.

PonsWarp가 웹 링크 기반 즉시 전송 서비스라면 Cloud Drop은 예외 상황을 위한 보조 기능이어야 합니다. 반대로 Cloud Drop이 중심이라면 PonsWarp는 임시 클라우드 파일 전달 서비스가 되고, 가격·계정·저장 안정성·만료·abuse 방어가 제품의 중심이 됩니다. 둘 다 가능하지만, 둘을 동시에 같은 무게로 들고 가면 검증해야 할 제품이 두 개가 됩니다.

기록은 이 갈림길을 보여줍니다. `4847872`는 delayed download를 해결하려 했고, `b6f3ea8`은 가격표를 만들었고, `f8f2120`과 `2e4593d`는 결제 권한을 붙였고, `3628858`은 대용량 업로드를 resumable multipart로 보강했습니다. `8f7299d`는 모바일 receiver가 백그라운드 후 돌아왔을 때 전송을 재개하는 문제를 다뤘고, `d88a625`는 GA4 production measurement를 붙였습니다. 이 흐름은 모두 합리적입니다. 다만 합리적인 조각들이 모이면서 제품의 중심 질문이 더 어려워졌습니다.

📐 설계 변경이 남긴 교훈

Cloud Drop이 붙으면서 설계의 기준도 바뀌었습니다. 직접 전송에서는 핵심 계약이 “양쪽이 연결되어 있을 때 파일을 깨지지 않게 이동한다”였습니다. Cloud Drop에서는 “서비스가 파일을 일정 시간 책임지고 맡는다”가 됩니다. 이 문장은 훨씬 무겁습니다.

책임이 무거워지면 관찰 가능성도 필요합니다. 업로드가 어느 part에서 실패했는지, 재개 가능한지, 저장소에는 실제로 어떤 객체가 남았는지, 만료 cleanup이 제대로 도는지, 결제 권한과 업로드 정책이 일치하는지 봐야 합니다. 그래서 readiness, production env, cleanup, analytics 같은 운영 표면이 더 중요해집니다. `d88a625`의 GA4 production measurement는 제품이 실제 사용 흐름을 측정하려 했다는 신호로 읽을 수 있습니다.

여기서 조심해야 할 점은 Cloud Drop을 붙였기 때문에 PonsWarp가 틀렸다고 말하지 않는 것입니다. 오히려 Cloud Drop은 제품이 현실을 마주했다는 증거입니다. 파일 전송은 “지금 바로 연결되는 두 브라우저”만으로 끝나지 않습니다. 사용자의 시간, 저장 비용, 실패 복구, 가격 정책까지 들어와야 합니다. 다만 그 현실을 받아들이는 순간, 제품은 더 좁고 선명한 약속을 필요로 했습니다.

🧭 지금 돌아보는 판단

지금 돌아보면 Cloud Drop은 PonsWarp가 제품이 되려던 순간에 붙은 기능이었습니다. 기술 실험이라면 직접 전송만으로도 충분히 흥미롭습니다. 하지만 실제 사용자는 상대가 지금 온라인인지, 모바일이 잠깐 잠겼는지, 링크를 나중에 열 수 있는지를 더 중요하게 느낍니다. Cloud Drop은 그 간극을 메우려는 정직한 시도였습니다.

아쉬운 지점은 Cloud Drop을 붙인 뒤 제품의 중심을 더 빨리 다시 써야 했다는 것입니다. “P2P가 기본이고 Cloud Drop은 보조다”인지, “Cloud Drop이 기본이고 P2P는 빠른 경로다”인지가 닫혔어야 했습니다. 이 결정이 닫히지 않으면 UI, pricing, entitlement, storage, analytics가 모두 각자 맞는 일을 하면서도 하나의 제품 문장으로 모이지 못합니다.

PonsWarp에서 Cloud Drop이 붙은 이유는 단순합니다. 직접 전송만으로는 사용자의 시간 문제를 해결할 수 없었기 때문입니다. 그러나 붙고 난 뒤의 문제는 단순하지 않았습니다. Cloud Drop은 기술 보완이면서 상품 후보였고, 상품 후보이면서 운영 책임이었습니다. 그 무게를 감당하려면 더 많은 기능보다 더 선명한 제품 선택이 먼저 필요했습니다.
