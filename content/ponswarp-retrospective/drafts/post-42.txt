그런데 왜 결국 살아남지 못했나

PonsWarp의 데스크톱 분기는 꽤 자연스러운 생각에서 나왔습니다. 웹에서 WebRTC DataChannel, 브라우저 저장 권한, worker, WASM, signaling 서버까지 밀어붙이다 보면 언젠가는 이런 질문을 하게 됩니다. “차라리 native로 내려가면 더 단순해지지 않을까?” QUIC를 쓰고, OS 파일 시스템에 더 직접 닿고, 브라우저의 제한을 덜 받으면 대용량 파일 전송 제품이 더 안정될 것처럼 보였습니다.

그 기대가 틀렸다고 말하기는 어렵습니다. 문제는 다른 곳에 있었습니다. 데스크톱은 웹의 실패를 지우는 대체재가 아니라, 이미 무거워진 제품 위에 또 하나의 제품 표면을 얹는 선택이었습니다. PonsWarp가 결국 살아남지 못한 이유는 기술적으로 아무것도 해결하지 못해서가 아닙니다. 오히려 너무 많은 문제를 실제로 해결하려고 했고, 그 해결의 폭이 제품이 감당할 수 있는 속도보다 빨리 넓어졌기 때문입니다.

💡 이 글은 “데스크톱을 만들었어야 했다/말았어야 했다”는 단순한 판정이 아닙니다. PonsWarp, pons-core-wasm, ponswarp-signaling-rs, ponswarp-desktop으로 이어진 기록을 기준으로, 왜 합리적인 기술 분기가 제품 생존으로 이어지지 못했는지를 정리합니다.

🧭 당시 제품 상태: 이미 웹만으로도 무거웠다

PonsWarp의 웹 앱은 단순한 파일 선택 화면이 아니었습니다. `src/App.tsx`와 `SenderView.tsx`, `ReceiverView.tsx`, `CloudSenderView.tsx`는 사용자에게 송신, 수신, Cloud Drop, 진행률, 실패 상태를 보여주는 제품 표면이었습니다. 그 아래에는 `simple-peer` 기반 WebRTC, sender/receiver worker, `DirectFileWriter`, `pons-core-wasm`, signaling backend가 놓였습니다.

초기에는 WebRTC로 바로 보내면 된다고 생각하기 쉬웠습니다. 하지만 기록은 곧 다른 방향으로 갔습니다. `638bc83`은 대용량 파일 다운로드 시 메모리 폭발을 막기 위해 들어갔고, `21dc9ba`는 전송 완료 후 수신자 저장까지 기다리는 양방향 핸드셰이크를 붙였습니다. `2def330`은 TURN 서버 설정을 동적으로 가져와 모바일 연결을 안정화하려 했고, `db175bf`와 `4650d02`는 청크 순서, 버퍼 관리, 파일 깨짐 문제를 계속 붙잡은 흔적입니다.

이 시점의 제품은 “파일을 보내는 웹앱”보다 훨씬 복잡했습니다. 사용자는 링크만 보고 들어오지만, 내부에서는 연결 성립, 네트워크 상태, 브라우저 큐, 저장 완료, 체크섬, 재정렬, 실패 복구가 모두 맞아야 했습니다. 웹이 가벼운 선택지였던 것이 아니라, 이미 웹 안에서 native에 가까운 책임을 떠안고 있었습니다.

🖥️ 데스크톱 분기의 매력

그래서 `ponswarp-desktop`이 2025-12-17에 만들어진 것은 뜬금없는 일이 아닙니다. 시리즈 계획의 표현대로 이 분기는 native, QUIC, Tauri에 대한 기대였습니다. 웹에서 계속 부딪힌 문제를 생각하면 그 기대는 충분히 이해됩니다.

첫째, 브라우저의 저장 경계가 답답했습니다. 웹에서는 사용자가 저장 권한을 줘야 하고, writer가 실제로 끝났는지 확인해야 하며, `bufferedAmount` 같은 sender 쪽 신호만 믿으면 안 됩니다. 그래서 ACK, `writer.waitForIdle()`, `DOWNLOAD_COMPLETE`, actual size 검증 같은 장치가 필요했습니다.

둘째, WebRTC DataChannel은 제품 설명과 구현 현실 사이의 간극이 컸습니다. 사용자에게는 “직접 전송”처럼 보이지만 실제로는 signaling, STUN/TURN, 모바일 네트워크, 브라우저 구현 차이, 재연결 상태가 얽힙니다. `ponswarp-signaling-rs`가 2025-12-10에 따로 생기고, 이후 `b834716`의 안정화와 배포 자동화, `f1c69cb`의 room cleanup deadlock 방어로 이어진 것은 서버가 결코 가벼운 매치메이커만은 아니었다는 증거입니다.

셋째, 성능과 무결성의 핵심은 이미 브라우저 JS 밖으로 내려가고 있었습니다. `pons-core-wasm`은 2025-12-04 `15aef19`로 시작됐고, `1b6fb15`의 ZIP64 스트리밍 압축, `58e6b89`의 재정렬 버퍼 WASM 마이그레이션, `e589cf2`의 압축·Merkle Tree·파일 서명 기능 추가, `7fe0ca1`의 암호화 지원 Zero-Copy Pool로 이어졌습니다. 이렇게 보면 “그렇다면 UI도 native로 가자”는 생각은 무리한 비약이 아니었습니다.

⚠️ 하지만 데스크톱은 탈출구가 아니라 두 번째 제품이었다

문제는 데스크톱이 기존 문제를 없애는 방식으로 들어오지 않았다는 점입니다. native 클라이언트가 생기면 브라우저 저장 권한은 덜 신경 쓸 수 있습니다. 하지만 대신 설치, 업데이트, OS별 파일 권한, 서명, 배포, 크래시 대응, UI parity, 웹 사용자와의 호환이라는 새 문제가 생깁니다.

PonsWarp의 핵심 가치는 원래 “상대에게 링크를 보내면 바로 들어와 받을 수 있다”에 가까웠습니다. 이 가치는 웹과 잘 맞습니다. 데스크톱은 더 강한 전송 엔진을 줄 수 있지만, 동시에 사용자의 첫 진입을 무겁게 만듭니다. 보내는 사람과 받는 사람이 모두 같은 앱을 깔아야 하는 순간, 제품은 단순한 웹 링크 공유에서 설치형 전송 도구로 성격이 바뀝니다.

더 큰 문제는 우선순위였습니다. 웹 앱은 여전히 고쳐야 할 것이 많았습니다. signaling 서버는 readiness, cleanup, TURN handling, production env를 요구했습니다. 브라우저 엔진은 backpressure, RTT adaptive control, partial recovery를 요구했습니다. 코어는 ZIP64, crypto, packet, reordering, file signature 같은 바이트 계약을 요구했습니다. 여기에 데스크톱까지 붙으면 “어느 표면이 정답인가”라는 질문이 새로 생깁니다.

제품이 살아남으려면 기술 선택지가 많아지는 것보다, 하나의 사용 흐름이 반복해서 성공하는 것이 먼저입니다. PonsWarp는 그 흐름을 닫기 전에 표면이 넓어졌습니다. 웹, 코어, signaling, Cloud Drop, 결제, analytics, 데스크톱이 모두 합리적인 이유로 등장했지만, 합리적인 조각이 많다고 해서 제품 전체가 단순해지는 것은 아니었습니다.

🔄 시스템 구조가 말해주는 실패 지점

PonsWarp의 구조를 네 층으로 보면 실패가 더 선명해집니다.

1층은 Product and UI입니다. React, Vite, Tailwind, Framer Motion, Zustand, SenderView/ReceiverView/CloudSenderView가 사용자의 선택과 상태를 설명합니다. 이 층은 제품의 언어를 맡습니다.

2층은 Browser transfer engine입니다. `simple-peer`, sender worker, receiver worker, adaptive chunk/batch, zero-copy packet pool, AES-256-GCM, ZIP64, backpressure가 실제 전송을 닫습니다. 이 층은 브라우저와 네트워크의 타협을 맡습니다.

3층은 Storage and recovery입니다. `DirectFileWriter`, StreamSaver, File System Access API, high/low watermark, partial recovery가 저장 완료의 진실성을 다룹니다. 이 층은 “화면에 완료라고 떠도 파일이 실제로 안전한가”를 맡습니다.

4층은 Core and backend입니다. `pons-core-wasm`은 compression, crypto, fec, packet, reordering buffer, zero-copy pool, ZIP64, file signature, merkle tree를 맡고, `ponswarp-signaling-rs`는 auth, billing, database, handlers, protocol, state, `/health`, `/ready`, `/ws`를 맡습니다. 이 층은 더 이상 보조 도구가 아니라 제품 신뢰의 바닥입니다.

데스크톱은 이 네 층 중 하나만 바꾸는 선택이 아니었습니다. UI 표면을 바꾸고, 전송 엔진을 바꾸고, 저장 경계를 바꾸고, backend와의 계약도 다시 생각하게 만드는 선택이었습니다. 그래서 “웹의 한계를 벗어나자”는 말은 실제로는 “제품 전체를 한 번 더 설계하자”에 가까웠습니다.

💸 제품화 구간에서 더 분명해진 문제

PonsWarp가 살아남지 못한 이유를 데스크톱만으로 설명하면 부족합니다. 2026년 5월 이후 기록은 다른 방향의 무게도 보여줍니다. `4847872`는 delayed downloads를 위한 async Cloud Drop을 붙였고, `b6f3ea8`은 Cloud Drop pricing page를 만들었고, `f8f2120`과 `2e4593d`는 Stripe Checkout과 PayPal billing으로 entitlement 흐름을 다뤘습니다. `3628858`은 대용량 Cloud Drop upload를 multipart resumable 구조로 만들었고, `a004c91`과 `212d751`은 Free plan 정책과 gated account/billing surface를 다시 흔들었습니다. `d88a625`는 GA4 production measurement를 붙였습니다.

이 흐름은 제품이 기술 실험을 넘어 실제 서비스가 되려 했다는 증거입니다. 하지만 동시에 문제의 종류가 바뀌었다는 신호이기도 합니다. 이제 질문은 “파일이 깨지지 않는가”만이 아니었습니다. “무료 10GB/24시간은 납득 가능한가”, “Cloud Drop은 P2P의 보완인가 별도 상품인가”, “결제 후 entitlement를 언제 어떻게 부여하는가”, “모바일 백그라운드 복귀 후 수신자는 어떻게 이어지는가”, “실제 사용자는 어느 경로에서 이탈하는가”가 같이 들어왔습니다.

기술적으로는 더 성숙해졌지만, 제품적으로는 더 많은 답을 동시에 요구받았습니다. 이 상태에서 데스크톱은 집중을 되찾는 도구가 아니라 또 하나의 선택지가 되기 쉬웠습니다.

🧱 실제 실패 지점: 해결 속도보다 늘어나는 질문

PonsWarp의 실패를 “기술력이 부족했다”로 정리하면 기록과 맞지 않습니다. 메모리 폭발, 저장 완료 핸드셰이크, TURN, 청크 순서, 파일 손상, 파이프라인 병렬화, backpressure, RTT adaptive control, WASM ZIP64, 재정렬 버퍼, signaling server, Cloud Drop, resumable multipart upload까지 많은 문제를 실제로 다뤘습니다.

오히려 실패 지점은 반대쪽에 있습니다. 해결한 문제가 늘어날수록 제품이 설명해야 할 범위도 같이 늘었습니다. 직접 전송인지, 클라우드 보관인지, 무료인지 유료인지, 웹인지 데스크톱인지, 동시에 온라인이어야 하는지 나중에 받아도 되는지, 실패하면 partial recovery를 믿어도 되는지, 모바일에서는 어떻게 이어지는지. 사용자가 이해해야 할 선택지가 많아졌고, 개발자가 검증해야 할 상태 공간도 커졌습니다.

파일 전송 제품은 기술적으로 단순하지 않습니다. 하지만 사용자는 단순하게 느껴야 합니다. PonsWarp는 내부를 단순하게 만들기 위해 많은 계층을 추가했고, 그 계층들은 각각 정당했습니다. 다만 최종 제품 경험은 그만큼 단순해지지 못했습니다. 이 차이가 생존을 어렵게 만들었습니다.

🧭 지금 돌아보는 판단

지금 돌아보면 데스크톱 분기는 틀린 욕망이 아니라 너무 늦게 온 정직한 질문에 가까웠습니다. 웹만으로 끝낼 수 없다는 감각은 맞았습니다. 브라우저 권한, DataChannel 큐, 모바일 네트워크, 저장 완료 검증은 실제로 어렵습니다. native/QUIC/streaming을 떠올리는 것은 자연스럽습니다.

하지만 제품의 생존은 “더 강한 기술 기반”만으로 결정되지 않습니다. PonsWarp에 필요했던 것은 한 번 더 강한 클라이언트가 아니라, 어떤 사용 흐름을 제품의 중심으로 고정할지에 대한 더 이른 결정이었습니다. 웹 링크 기반 즉시 전송을 끝까지 밀 것인지, Cloud Drop을 중심 상품으로 바꿀 것인지, 데스크톱을 고신뢰 전송 도구로 따로 세울 것인지가 먼저 닫혔어야 했습니다.

그 결정이 닫히지 않은 상태에서 기술 층은 계속 성숙했습니다. 그래서 역설적으로 더 좋은 코어, 더 강한 서버, 더 많은 복구 장치가 생겼지만, 제품은 더 명확해지지 않았습니다. PonsWarp가 살아남지 못한 이유는 무언가 하나가 크게 망가져서가 아니라, 여러 방향으로 동시에 맞는 선택을 하다가 하나의 제품으로 좁히는 힘을 잃었기 때문입니다.
