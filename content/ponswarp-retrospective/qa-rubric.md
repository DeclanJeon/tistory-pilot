# PonsWarp 회고 시리즈 QA 기준

## 목적

이 문서는 회고 글 초안과 발행 결과를 같은 기준으로 점검하기 위한 QA 기준서다. 글이 잘 써졌는지뿐 아니라, 근거와 구조, Tistory 렌더링, 공개 결과까지 같이 본다.

## 1. 구조 QA

### 필수 조건

- 도입이 2~3문장 안에 문제를 제시해야 한다.
- 본문은 4~6개 핵심 섹션을 가져야 한다.
- 섹션 헤더에는 이모지가 붙어야 한다.
- 마지막에는 `읽은 코드` 성격의 정리 구간이 있어야 한다.
- 글이 감상문으로만 끝나지 않고 시스템 구조 설명을 포함해야 한다.

### 실패 조건

- 모든 섹션이 같은 길이와 같은 리듬으로 끝나는 경우
- 문단이 전부 설명형 평서문으로만 밀려가는 경우
- 스토리와 구조 설명이 분리되지 않는 경우

## 2. 톤 QA

### 필수 조건

- `~합니다` 체를 유지한다.
- 실제 날짜, 커밋, 파일명 같은 구체성이 있다.
- 너무 정답처럼 말하지 않는다.
- 오판과 한계를 숨기지 않는다.

### 금지 표현

- `한 줄 요약`
- `먼저 핵심만 보자`
- `결론적으로`
- `바로 본론으로`
- `시사하는 바가 크다`

## 3. 근거 QA

### 필수 조건

- 글마다 실제 커밋 3개 이상이 들어간다.
- 핵심 주장에는 코드 파일 또는 커밋이 연결돼 있어야 한다.
- 현재 접근 불가능한 저장소는 과장 없이 다룬다.

### 점검 질문

- 이 문장이 실제 커밋 메시지나 코드 구조로 뒷받침되는가
- 이 판단 변화가 너무 나중의 시점을 앞당겨 설명하고 있지는 않은가
- 공개 기록만으로 말할 수 있는 수준을 넘지 않았는가

## 4. 서비스 분석 QA

각 글은 아래 항목 중 최소 6개 이상을 포함해야 한다.

- 프로젝트 구성
- 디자인 패턴
- 기술 스택
- 사용자 플로우
- 시스템 플로우
- 기능 구조
- 핵심 로직
- 알고리즘
- 운영/배포 관점
- 제품 판단 변화

## 5. 시각 자료 QA

### 필수 조건

- 글당 2~4개 이미지 또는 다이어그램이 있어야 한다.
- 이미지는 장식이 아니라 설명 역할을 해야 한다.
- 각 이미지는 캡션을 가져야 한다.
- 본문에서 이미지를 왜 보는지 먼저 설명해야 한다.

### 실패 조건

- 제품과 상관없는 분위기용 이미지
- 다이어그램이 본문과 분리돼 따로 노는 경우
- 캡션 없이 이미지만 들어간 경우

## 6. HTML QA

### 필수 조건

- 마크다운 fence가 없어야 한다.
- Tistory에서 깨지는 `<details>`, `<summary>`를 쓰지 않는다.
- `<figure>`, `<figcaption>` 구조를 유지한다.
- 표는 모바일에서도 읽을 수 있게 감싸야 한다.
- 다크 코드 참조 박스가 들어가야 한다.

### 점검 질문

- 본문 HTML이 직접 렌더링돼도 문단 간격이 무너지지 않는가
- 이미지 크기와 캡션이 과하게 크거나 작지 않은가
- 인라인 코드, 볼드, 박스 스타일이 한 글 안에서 일관적인가

## 7. 발행 QA

### 발행 전

- 제목과 body file이 일치하는가
- 카테고리 지정이 맞는가
- 이미지 src가 실제 사용 가능한가
- 본문에 로컬 경로가 남아 있지 않은가

### 발행 후

- 제목이 맞는가
- 이미지가 로드되는가
- 카테고리가 맞는가
- 마크다운 누출이 없는가
- 공개 URL이 저장됐는가

## 8. 시리즈 일관성 QA

- 앞글과 다음 글의 연결 문장이 과하지 않은가
- 같은 커밋을 반복해서 설명할 때 관점이 겹치지 않는가
- 한 글에서 이미 다룬 구조를 다음 글에서 다시 처음부터 반복하지 않는가
- PonsWarp를 영웅담처럼 포장하지 않는가

## 9. 판정 레벨

### PASS
- 구조, 톤, 근거, HTML, 발행 결과가 모두 기준 충족

### REVISE
- 핵심은 맞지만 AI 냄새, 구조 균일화, 근거 부족, HTML 문제 중 하나라도 보임

### BLOCK
- 근거 없는 주장
- 잘못된 커밋 인용
- 렌더링 깨짐
- 발행 후 이미지/카테고리 오류
