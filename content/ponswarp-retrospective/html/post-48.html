PonsWarp에 analytics를 붙인 일은 화려한 기능 추가가 아니었습니다.

WebRTC 전송, 저장 완료 핸드셰이크, WASM 코어, Rust signaling 서버, Cloud Drop, 결제와 entitlement까지 지나온 뒤에 붙은 측정 계층이었습니다. 기록상으로는 2026-06-08 d88a625 Enable production traffic measurement with GA4가 그 지점입니다.

이 커밋은 파일을 더 빠르게 보내게 만들지도 않았고, Cloud Drop 용량을 늘리지도 않았습니다. 하지만 제품을 보는 방식은 꽤 크게 바꿉니다. analytics가 들어오면 질문은 “실제 사용자는 어디로 들어오고, 어디서 멈추고, 어떤 선택지를 보기도 전에 나가는가”로 달라집니다.

💡 이 글은 GA4 설정법이 아니라, 측정이 늦게 들어왔을 때 비로소 보이는 제품 구조와 판단 비용에 대한 회고입니다.

🧭 당시 제품 상태: 기능은 많았지만 관찰은 늦었다

PonsWarp는 처음부터 측정 중심 제품이 아니었습니다. 시작점은 대용량 파일을 브라우저에서 직접 보내겠다는 기술적 실험에 가까웠습니다. ad322f3 이후 638bc83의 메모리 폭발 방지, 21dc9ba의 수신 저장 완료 핸드셰이크, 2def330의 TURN 동적 설정, db175bf와 4650d02의 청크 순서와 파일 손상 수정이 이어졌습니다.

이 구간에서 중요한 것은 실제 사용자가 어디서 이탈하는지보다, 파일이 깨지지 않고 끝까지 닫히는지였습니다. 파일 전송 제품에서 무결성이 흔들리면 analytics를 붙여도 의미가 없습니다.

그 뒤에는 949d921의 파이프라인 병렬화와 이중 버퍼링, 54cf5f4의 backpressure, 09161ce의 RTT 기반 동적 혼잡 제어가 들어왔습니다. pons-core-wasm도 ZIP64, 재정렬 버퍼, Merkle Tree, 파일 서명, zero-copy, crypto 같은 바이트 계약을 맡았습니다.

그러나 이 모든 것은 내부 정합성의 문제였습니다. 시스템은 점점 더 똑똑해졌지만, 제품은 여전히 사용자의 실제 경로를 충분히 보고 있지 못했습니다.

📦 제품화가 만든 측정의 필요

2026년 5월 이후 PonsWarp는 서비스에 가까운 형태로 이동했습니다. 4847872는 async Cloud Drop을 붙였고, b6f3ea8은 Cloud Drop pricing page를 만들었습니다. f8f2120과 2e4593d는 Stripe Checkout과 PayPal billing으로 entitlement 흐름을 다뤘고, 3628858은 대용량 Cloud Drop upload를 multipart resumable 구조로 만들었습니다.

direct transfer만 있을 때 질문은 두 사람이 동시에 온라인일 수 있는가, 네트워크가 붙는가, 저장이 끝나는가였습니다. Cloud Drop이 붙으면 보내는 사람은 상대가 나중에 받아도 된다는 가치를 이해하는가, 무료 10GB/24시간 정책은 비용을 감당할 수 있는가, 유료 결제는 언제 등장해야 거부감이 덜한가로 질문이 바뀝니다.

a004c91은 Free plan을 first-class cloud policy로 노출했고, 212d751은 gated account와 billing surface를 비활성화했습니다. 정책은 코드로 표현됐지만, 실제로 맞는지는 사용자 흐름을 봐야 합니다.

🔎 analytics가 보여주는 것은 정답이 아니라 빈칸이다

GA4 production measurement를 붙였다고 해서 갑자기 제품의 답이 나오는 것은 아닙니다. analytics는 “왜”를 자동으로 설명하지 않습니다. 다만 그동안 감으로만 말하던 빈칸을 드러냅니다.

direct transfer가 중심이라고 믿었는데 실제 트래픽이 Cloud Drop 설명이나 pricing 근처에서 더 오래 머문다면, 제품 언어를 다시 봐야 합니다. 반대로 Cloud Drop을 수익화의 중심으로 생각했는데 사용자가 파일 선택 전에 나간다면, 문제는 결제가 아니라 첫 화면의 약속일 수 있습니다. 모바일 수신 복귀를 고친 8f7299d 같은 기록도 실제 흐름에서 봐야 의미가 닫힙니다.

🧱 시스템 구조: 측정은 가장 위에 있지만 가장 늦게 닫힌다

PonsWarp의 1층은 Product and UI입니다. src/App.tsx, SenderView.tsx, ReceiverView.tsx, CloudSenderView.tsx가 direct transfer와 Cloud Drop의 선택지를 보여줍니다. 2층은 simple-peer, sender/receiver worker, adaptive chunk/batch, AES-256-GCM, ZIP64, backpressure가 맡는 Browser transfer engine입니다.

3층은 DirectFileWriter, StreamSaver, File System Access API, high/low watermark, partial recovery가 있는 Storage and recovery입니다. 4층은 pons-core-wasm과 ponswarp-signaling-rs가 맡는 Core and backend입니다.

analytics는 이 네 층을 대체하지 않습니다. 하지만 네 층이 사용자에게 어떤 순서로 체감되는지 확인하게 만듭니다. 내부 계층은 아래에서 위로 쌓이지만, 사용자의 경험은 위에서 아래로 내려갑니다.

⚠️ 실제 실패 지점: 숫자를 보기 전까지는 모든 선택이 그럴듯했다

analytics가 없을 때 제품 판단은 설계자의 직감에 기대게 됩니다. PonsWarp에서는 direct transfer도 그럴듯했고, Cloud Drop도 그럴듯했고, 무료 10GB/24시간도 그럴듯했고, PayPal entitlement도 그럴듯했습니다. 각각의 기능은 따로 보면 충분히 합리적이었습니다.

문제는 합리적인 선택지가 많아질수록 제품의 중심이 흐려진다는 점입니다. 실제 사용자가 어느 흐름을 기대하고 들어오는지 모르면, 모든 기능이 “중요해 보이는 상태”로 남습니다.

🔄 설계 변경: 기능 중심에서 경로 중심으로

analytics 이후의 설계 변경은 코드 구조보다 사고방식에 가깝습니다. 이전에는 WebRTC가 붙는가, 저장이 끝나는가, Cloud Drop upload가 재개되는가, 결제 후 entitlement가 발급되는가를 물었습니다.

측정이 들어오면 사용자는 어떤 진입점에서 시작하는가, direct transfer와 Cloud Drop 중 무엇을 먼저 이해하는가, pricing은 설득 페이지인가 차단 페이지인가, 무료 정책은 체험을 열어주는가 유료 전환을 애매하게 만드는가를 묻게 됩니다.

GA4 production measurement는 로컬에서만 만족하는 기능이 아닙니다. production traffic을 봐야 의미가 있습니다. /health, /ready, signaling room cleanup, billing webhook, resumable upload와 마찬가지로 analytics도 운영 환경에서만 닫히는 계약입니다.

🧭 지금 돌아보는 판단

PonsWarp에 analytics가 늦게 붙은 것은 이상한 일이 아닙니다. 제품의 바닥이 불안한 상태에서 측정부터 붙이는 것은 허영에 가깝습니다. 파일이 깨지고, 저장 완료가 거짓이고, 모바일이 끊기고, 서버 cleanup이 deadlock을 만들면 방문자 수를 보는 일은 본질이 아닙니다.

하지만 Cloud Drop, pricing, entitlement, free plan, PayPal, mobile resume까지 붙은 뒤에도 측정이 없으면 제품은 여전히 개발자의 머릿속에서만 닫힙니다. 실제 사용자는 그 머릿속 순서대로 움직이지 않습니다.

PonsWarp가 analytics를 붙이고 나서야 본 것은 숫자 자체가 아니라, 제품이 이미 너무 많은 가정을 품고 있었다는 사실입니다. direct transfer가 중심인지, Cloud Drop이 중심인지, 무료 정책이 초대장인지 비용 폭탄인지, 결제 표면이 설득인지 방해인지는 코드만 읽어서는 닫히지 않습니다.
