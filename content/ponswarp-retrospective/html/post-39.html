PonsWarp를 만들면서 가장 자주 들었던 마음은 “이걸 왜 굳이 웹에서 하고 있지?”였습니다.

처음에는 WebRTC로 브라우저끼리 직접 파일을 보내면 서버 비용도 줄고, 설치도 필요 없고, 링크 하나로 끝나는 서비스가 될 거라고 생각했습니다. 그런데 실제로는 브라우저가 편해서 고른 플랫폼이 아니라, 브라우저의 제약을 매일 설득해야 하는 플랫폼이 되었습니다.

메모리 폭발을 막아야 했고, DataChannel의 bufferedAmount가 수신 저장 완료를 뜻하지 않는다는 사실을 받아들여야 했고, 모바일에서는 TURN 없이는 연결 자체가 흔들렸습니다. 저장은 또 다른 문제였습니다. 사용자는 “다운로드 완료”라는 말을 믿지만, 브라우저 내부에서는 File System Access API, StreamSaver, worker, writer idle, actualSize 검증이 맞물려야 겨우 그 말을 할 수 있었습니다.

그래서 어느 순간 웹을 포기하고 싶었습니다. 이 감정은 단순한 투정이 아니었습니다. PonsWarp의 구조가 커질수록 “웹이 제품에 맞는가”라는 질문은 실제 설계 질문이 되었습니다. 그리고 그 질문이 결국 ponswarp-desktop 분기로 이어졌습니다.

💡 이 글은 데스크톱이 정답이었다는 글이 아닙니다. PonsWarp가 왜 웹을 버리고 싶어졌는지, native / QUIC / Tauri 같은 선택지가 왜 매력적으로 보였는지, 그리고 왜 그 충동만으로 제품 판단을 끝낼 수 없었는지를 정리합니다.

🧱 당시 제품 상태

post-31부터 post-38까지의 서버 구간에서 이미 한 가지가 분명해졌습니다. “서버 없는 전송”이라는 말은 절반만 맞았습니다. 파일 바이트는 P2P로 흐를 수 있지만, 방 생성, signaling, TURN 설정, readiness, cleanup, 운영 환경은 서버를 피해가지 못했습니다. ponswarp-signaling-rs가 2025-12-10 44fb5ad로 분리된 뒤에도, b834716의 안정성·배포 자동화, f1c69cb의 cleanup deadlock 방지는 계속 필요했습니다.

브라우저 쪽도 가벼운 화면 앱이 아니었습니다. React 19, Vite 7, Tailwind 4, Framer Motion, Zustand는 제품 표면을 만들었고, simple-peer 기반 WebRTC, sender/receiver worker, adaptive chunk/batch, AES-256-GCM, ZIP64, zero-copy packet pool, backpressure는 전송 엔진을 만들었습니다. 저장 계층에는 directFileWriter.ts, StreamSaver, File System Access API, high/low watermark, partial recovery가 얽혔습니다.

이 구조는 “웹 앱”이라는 말보다 훨씬 무거웠습니다. 사용자는 브라우저 탭 하나를 보고 있었지만, 내부에는 UI, signaling, WebRTC, worker, WASM core, 저장 writer, 검증 로직이 붙어 있었습니다. 웹을 포기하고 싶었던 날은 이 구조가 보이기 시작한 날이기도 했습니다.

🌐 웹이 힘들었던 지점

첫 번째 압력은 브라우저 권한 모델이었습니다. 파일 전송 서비스는 파일을 읽고, 오래 붙잡고, 큰 데이터를 나누고, 마지막에는 사용자의 디스크에 안전하게 써야 합니다. 그런데 웹은 이런 일을 항상 사용자 권한과 탭 생명주기 안에서 처리합니다. 설치형 앱처럼 파일 시스템을 자연스럽게 잡고 있는 환경이 아닙니다.

두 번째 압력은 네트워크 제어였습니다. WebRTC DataChannel은 좋은 선택이었지만, 대용량 파일 전송에서는 추상화가 너무 얇게 느껴졌습니다. 638bc83의 대용량 다운로드 메모리 폭발 방지, 6e635f3의 Push 방식과 AIMD 혼잡 제어, 2def330의 동적 TURN 설정, 54cf5f4의 receiver-side backpressure, 09161ce의 RTT 기반 동적 혼잡 제어는 모두 같은 사실을 말합니다. 브라우저에서 P2P 전송을 한다는 것은 연결만 붙이는 일이 아니라, 큐와 저장 속도와 네트워크 지연을 계속 관찰하는 일이었습니다.

세 번째 압력은 완료 표시였습니다. 21dc9ba에서 수신자 저장까지 기다리는 양방향 핸드셰이크가 들어갔고, db175bf, 8aff234, 4650d02 같은 파일 손상과 완료 중복 방어가 이어졌습니다. “전송 완료”라는 말이 sender의 전송 종료인지, receiver의 수신 종료인지, 디스크 저장 완료인지, 크기와 체크섬이 맞는지에 따라 전혀 다른 의미가 되었습니다.

이 세 압력이 겹치면 웹은 답답해 보입니다. 브라우저의 보안 모델은 제품 속도를 늦추는 것처럼 보이고, DataChannel의 큐는 수신 저장 상태를 대신 말해주지 않고, 모바일 탭은 네트워크와 생명주기에 취약합니다. 그때 데스크톱이 좋아 보이는 것은 자연스러운 반응이었습니다.

🖥️ 데스크톱이 좋아 보였던 이유

ponswarp-desktop은 2025-12-17에 만들어진 분기였습니다. evidence-index는 이 저장소의 관찰 포인트를 native / QUIC / Tauri로 기록하고, late visible activity를 2026-02-18로 둡니다. 이 정도 근거만으로 세부 구현을 과장할 수는 없습니다. 다만 왜 그 방향이 매력적으로 보였는지는 PonsWarp 본체의 실패 기록만으로도 설명할 수 있습니다.

native streaming은 브라우저 저장 API의 우회로처럼 보였습니다. 설치형 앱은 파일 시스템과 더 가깝고, 긴 전송 작업을 탭 생명주기보다 안정적으로 붙잡을 수 있을 것처럼 보입니다. QUIC는 WebRTC DataChannel보다 전송 제어를 더 직접적으로 설계할 수 있는 길처럼 보였습니다. Tauri는 웹 UI의 생산성을 유지하면서 native 권한과 패키징을 붙일 수 있는 절충안처럼 보였습니다.

제품 구조로 보면 이 유혹은 꽤 합리적입니다. 사용자는 여전히 파일을 고르고 링크나 코드로 상대와 연결됩니다. 하지만 내부는 browser worker와 File System Access API 대신 native file writer, QUIC stream, OS-level permission, desktop packaging으로 바뀔 수 있습니다. 문제는 이것이 모든 책임을 없애는 것이 아니라 책임의 위치를 옮긴다는 데 있었습니다.

⚖️ 플랫폼을 바꾸면 사라지는 것과 남는 것

웹을 포기하면 몇 가지 문제는 줄어들 수 있습니다. 저장 권한을 매번 브라우저 방식으로 설명하지 않아도 되고, 큰 파일을 탭 안에서 오래 다루는 부담도 줄어들 수 있습니다. browser DataChannel의 bufferedAmount와 저장 완료의 간극도 다른 네트워크/IO 모델로 다시 설계할 수 있습니다. 모바일 브라우저의 backgrounding 문제도 데스크톱 앱에서는 덜 직접적인 문제가 됩니다.

하지만 남는 문제가 더 중요했습니다. 파일 전송 제품은 플랫폼과 무관하게 무결성을 증명해야 합니다. packet encode/decode, encryption, ZIP64, reordering buffer, CRC32, Merkle tree, file signature 같은 바이트 계약은 웹을 버린다고 사라지지 않습니다. pons-core-wasm의 15aef19, 1b6fb15, e589cf2, 7fe0ca1 흐름은 오히려 플랫폼을 넘어서 재사용 가능한 코어 계약이 필요하다는 쪽에 가깝습니다.

운영도 사라지지 않습니다. P2P라고 해도 signaling, 방 상태, readiness, cleanup, TURN 같은 서버 책임은 남습니다. 데스크톱 앱이 되면 오히려 배포, 업데이트, OS별 권한, 코드 서명, 설치 실패, 버전 호환성 같은 새로운 제품 운영 문제가 생깁니다. 웹에서 힘들었던 문제를 native가 모두 지워주는 것이 아니라, 다른 종류의 비용으로 바꾸는 셈입니다.

사용자 플로우도 달라집니다. 웹은 링크 하나로 들어오는 장점이 있습니다. 상대에게 “앱을 설치해 달라”고 말하는 순간, PonsWarp의 가장 강한 진입 장벽 없는 공유 흐름이 약해집니다.

🔄 그래서 판단은 더 어려워졌다

웹을 포기하고 싶었던 날의 핵심은 “웹은 나쁘고 데스크톱은 좋다”가 아니었습니다. 더 정확히는 PonsWarp가 두 개의 서로 다른 욕망 사이에 끼어 있었다는 점입니다.

하나는 설치 없는 공유입니다. 파일을 보내는 사람이 링크를 만들고, 받는 사람이 브라우저로 들어오고, 둘이 동시에 열려 있으면 바로 전송이 시작되는 흐름입니다. 이 흐름은 웹의 장점입니다. PonsWarp가 처음에 매력적으로 보였던 이유도 여기에 있었습니다.

다른 하나는 긴 파일 전송 작업을 안정적으로 붙잡는 능력입니다. 수 GB 파일, 느린 네트워크, 모바일 환경, 저장 완료 검증, 재시도와 복구를 생각하면 웹은 계속 불편합니다. 이 흐름에서는 native가 좋아 보입니다.

그러므로 데스크톱 분기는 실패의 도피라기보다 제품 질문의 분기였습니다. “우리는 설치 없는 접근성을 더 중요하게 볼 것인가, 아니면 장시간 전송의 제어권을 더 중요하게 볼 것인가?” 이 질문을 직접 마주하게 만든 것이 ponswarp-desktop이었습니다.

🚫 그날의 충동이 정답은 아니었다

돌아보면 웹을 포기하고 싶었던 감정은 정직했지만, 그것만으로 결정을 내리면 위험했습니다. 힘든 계층에서 벗어나고 싶다는 마음은 종종 새로운 계층의 비용을 과소평가합니다. 브라우저에서 파일 저장이 힘들다고 해서 desktop packaging이 쉬워지는 것은 아닙니다. WebRTC가 답답하다고 해서 QUIC 제품화가 자동으로 쉬워지는 것도 아닙니다.

또 PonsWarp의 신뢰 문제는 플랫폼 문제가 아니라 제품 계약 문제였습니다. 완료 표시가 거짓말하지 않게 만들고, 수신 저장 완료를 확인하고, 깨진 파일을 성공처럼 보이지 않게 하고, 실패했을 때 사용자가 믿을 수 있는 상태를 보여주는 일은 웹에서도 필요하고 데스크톱에서도 필요합니다.

그날의 판단은 “웹을 버리자”가 아니라 “웹을 절대시하지 말자”에 가까웠습니다.

🧭 지금 돌아보는 판단

지금 돌아보면 웹을 포기하고 싶었던 날은 PonsWarp가 플랫폼 환상에서 벗어난 날이었습니다. 처음에는 웹이면 설치가 없고, P2P면 서버가 가볍고, Rust/WASM이면 성능과 무결성이 잡힐 것처럼 보였습니다. 하지만 실제 제품은 그렇게 단순하지 않았습니다.

웹은 한계였습니다. 동시에 제품의 가장 중요한 표면이기도 했습니다. 링크 기반 진입, 즉석 공유, 상대가 별도 설치 없이 들어오는 흐름은 웹이 아니면 약해졌습니다. 반대로 데스크톱은 매력적인 탈출구였지만, 신뢰·복구·운영·배포의 책임을 없애지는 못했습니다.

그래서 post-39의 결론은 포기가 아니라 기준입니다. 플랫폼은 문제를 해결하는 마법이 아니라 실패 모드를 배치하는 방식입니다. PonsWarp가 웹에서 힘들었던 이유를 제대로 이해해야 데스크톱 분기의 의미도 제대로 볼 수 있습니다. 그 다음 글에서 다룰 ponswarp-desktop은 바로 이 기준 위에서 읽어야 합니다.
