PonsWarp가 Cloud Drop을 붙인 뒤부터 제품의 질문은 조금 달라졌습니다.

처음에는 “상대가 지금 온라인이 아니어도 파일을 받을 수 있게 할 수 있는가”가 핵심이었습니다. 그런데 Cloud Drop이 들어오자마자 무료 범위, 유료 경계, 계정, entitlement가 따라왔습니다.

무료 정책은 단순한 가격표가 아니었습니다. 10GB, 24시간, Cloud Drop, 계정 같은 단어가 한 화면에 올라오는 순간 사용자는 그것을 내부 실험이 아니라 제품 약속으로 읽습니다. 그래서 free plan rollback은 돈을 포기한 기록이 아니라, 아직 감당하지 못한 약속을 제품 표면에서 한 번 내린 판단에 가깝습니다.

💡 이 글은 “무료가 좋다”거나 “유료화가 나쁘다”는 이야기가 아닙니다. 4847872, b6f3ea8, 2e4593d, a004c91, 212d751로 이어지는 제품화 흐름 안에서 가격 정책이 제품 구조를 얼마나 빨리 바꾸는지 보는 글입니다.

🧭 rollback은 왜 판단의 흔적이 되었나

Cloud Drop 이전의 PonsWarp는 어렵지만 비교적 단순한 약속을 했습니다. sender와 receiver가 같은 시간에 들어오고, WebRTC 연결이 붙고, 파일이 깨지지 않고, receiver가 저장 완료를 확인하면 전송이 끝납니다.

Cloud Drop은 이 약속을 바꿉니다. receiver가 지금 없어도 됩니다. sender가 업로드를 끝내면 서버 쪽 저장소가 일정 시간 파일을 들고 있고, receiver는 나중에 내려받습니다. 사용자 관점에서는 편해지지만 제품 관점에서는 “누가 언제까지 무엇을 책임지는가”가 완전히 달라집니다.

무료 10GB / 24시간은 마케팅 문구처럼 보이지만 실제로는 저장 비용, abuse 방지, 업로드 재개, 다운로드 실패, 모바일 복귀, 만료 처리, 지원 문의의 범위를 정합니다. rollback은 그 착시를 늦게라도 걷어 낸 조치였습니다.

🧱 당시 제품 상태: 기능은 붙었지만 약속은 아직 무거웠다

제품화 구간의 커밋들은 속도가 빠릅니다. 4847872는 지연 다운로드를 위한 async Cloud Drop을 열었습니다. b6f3ea8은 Cloud Drop pricing page를 first-class로 추가했습니다. f8f2120과 2e4593d는 Stripe Checkout에서 PayPal로 이어지는 entitlement 흐름을 만들었습니다. 3628858은 대용량 Cloud Drop 업로드를 resumable multipart uploads로 바꿨고, a004c91은 Free plan을 first-class cloud policy로 노출했습니다.

이 흐름만 보면 제품이 빠르게 성숙해지는 것처럼 보입니다. 하지만 Cloud Drop은 전송 플로우의 확장이고, pricing page는 구매 판단의 표면이고, entitlement는 계정/권한 시스템이며, resumable upload는 실패 복구 구조입니다. Free plan은 이 모든 것을 사용자에게 하나의 약속으로 묶어 버립니다.

그래서 212d751 Disable gated account and billing surfaces가 중요합니다. 이 커밋은 단순히 결제 버튼을 숨긴 사건이 아니라, 가격표가 있는 서비스처럼 행동하기 전에 전송과 Cloud Drop의 신뢰 조건을 더 확인해야 한다는 판단을 보여 줍니다.

⚙️ 시스템 구조로 보면 무엇이 되돌아갔나

무료 플랜 rollback을 UI 변경으로만 보면 핵심을 놓칩니다. PonsWarp의 구조에서 free / paid 정책은 Product and UI, Browser transfer engine, Storage and recovery, Core and backend 네 층을 모두 건드립니다.

SenderView와 CloudSenderView에 가격과 계정 문구가 끼어들면 사용자는 전송 도구를 쓰는 것이 아니라 서비스 플랜을 고르는 상태가 됩니다. 직접 전송은 WebRTC DataChannel, worker, backpressure, receiver 저장 완료의 문제지만 Cloud Drop은 upload session, chunked upload, retry, server-side object lifecycle 쪽으로 무게가 이동합니다.

Storage and recovery 층에서도 “업로드가 끝났다”와 “다운로드가 안전하게 끝났다”는 분리되어야 합니다. Core and backend 층에서는 signaling 서버가 파일 전달의 보조 장치가 아니라 상품 접근권을 판정하는 control plane이 됩니다. rollback은 이 control plane을 없앤 것이 아니라, 너무 이른 시점에 제품 표면으로 올리는 일을 멈춘 것입니다.

🚧 실제 실패 지점: 가격보다 신뢰가 먼저였다

무료 플랜을 공개하면 사용자는 제한을 기억합니다. 10GB까지 되는구나. 24시간은 보관되는구나. 계정이 있으면 더 큰 파일이나 더 긴 보관이 되겠구나. 이 기억은 구현 상세를 기다려 주지 않습니다. 실패가 나면 “베타라서”가 아니라 “약속이 깨졌다”가 됩니다.

PonsWarp는 이미 신뢰 문제에 오래 붙잡혀 있었습니다. 21dc9ba의 저장 완료 handshake, 4650d02의 파일 깨짐 문제 해결, 54cf5f4의 receiver-side backpressure는 모두 속도나 표면보다 신뢰 조건이 먼저라는 판단이었습니다.

Free plan rollback은 무료 사용자를 줄이기 위한 결정이 아니라, 아직 한 화면에서 만나기 어려운 사용자 기대, 운영 비용, entitlement, recovery 책임을 분리한 결정이었습니다.

🔄 설계 변경: 팔기 전에 덜 약속하기

rollback 이후의 더 나은 질문은 “어떻게 유료화할까”가 아니라 “무엇을 제품 약속으로 내걸 수 있는가”였습니다. Cloud Drop 자체는 필요했습니다. 사용자가 동시에 온라인이어야 한다는 직접 전송의 제약은 실제 제품 플로우에서 큽니다.

4847872가 열어 둔 async Cloud Drop 방향과 3628858의 resumable multipart uploads는 그 문제를 정면으로 다룹니다. 되돌린 것은 Cloud Drop이 아니라 순서였습니다. 가격표와 계정 문구를 먼저 세우고 신뢰 조건을 맞추는 순서가 아니라, 실패 복구와 모바일 복귀와 운영 측정을 더 확인한 뒤 약속의 크기를 정하는 순서입니다.

2026-05-17 8f7299d의 모바일 receiver backgrounding 복구, 2026-06-08 d88a625의 GA4 production traffic measurement는 이 관점에서 이어지는 기록으로 읽을 수 있습니다. 팔기 전에 실제 사용 흐름을 더 봐야 했습니다.

⚖️ 지금 돌아보는 판단

지금 돌아보면 free plan rollback은 부끄러운 후퇴라기보다 필요한 제동이었습니다. 제품을 만들다 보면 가격 정책을 붙이는 순간 갑자기 서비스가 된 것 같은 기분이 듭니다. 하지만 파일 전송 제품에서 구조의 완성은 가격표가 아니라 실패한 전송을 얼마나 정직하게 다루는가에 있습니다.

PonsWarp는 이미 여러 번 이 사실을 배웠습니다. 완료 표시는 저장 완료 이후여야 했고, 빠른 전송보다 무결성이 먼저였고, 서버 없는 전송이라는 말은 절반만 맞았습니다. free plan rollback은 같은 교훈이 제품화와 돈의 문제에서 다시 나타난 장면입니다.

그래서 이 판단은 소극적인 결정이 아니었습니다. 제품 표면을 줄여서 신뢰 조건을 다시 앞에 세운 결정이었습니다. 이후의 질문은 “얼마를 받을까”보다 “어떤 실패까지 책임질 수 있을까”에 가까워졌습니다.
