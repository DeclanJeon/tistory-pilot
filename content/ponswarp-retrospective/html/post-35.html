PonsWarp에서 파일 바이트는 signaling 서버를 지나가지 않습니다.

사용자가 큰 파일을 보내면 실제 데이터는 WebRTC DataChannel을 타고 브라우저와 브라우저 사이를 흐릅니다. 그래서 처음에는 signaling 서버를 가볍게 생각하기 쉽습니다. 방을 만들고, 상대를 알려주고, offer와 answer, ICE candidate만 넘겨주면 되는 매치메이커처럼 보입니다.

하지만 제품을 만들다 보면 사용자는 내부 경로를 그렇게 나눠서 보지 않습니다. 상대가 방에 들어왔는지, 연결 준비가 되었는지, 모바일에서 붙는지, 서버가 살아 있는지, 실패했을 때 다시 시도해도 되는지를 한 덩어리로 경험합니다.

💡 이 글은 signaling 서버가 “그냥 중계 서버”에서 제품 신뢰의 첫 관문으로 바뀐 순간을 정리합니다. 근거는 Rust 서버 전환, 방 관리, WebSocket 프로토콜, TURN fallback, readiness, cleanup deadlock 수정 기록입니다.

🧭 당시 제품 상태

PonsWarp의 초반 약속은 서버 없는 전송에 가까웠습니다. 링크를 열고, 상대가 들어오고, WebRTC가 붙으면 파일은 직접 흐릅니다. 이 구조는 제품 설명으로는 매력적입니다.

그런데 WebRTC 제품에서 “서버가 없다”는 말은 절반만 맞습니다. peer가 서로를 찾으려면 방과 peer 목록이 필요합니다. 브라우저끼리 SDP offer와 answer를 주고받아야 하고, 네트워크 경로를 찾기 위해 ICE candidate도 전달해야 합니다.

시리즈 앞부분에서 다룬 2def330은 TURN 서버 설정을 동적으로 가져와 모바일 WebRTC 연결 안정화를 시도한 기록입니다. 이후 44fb5ad에서 Rust 기반 ponswarp-signaling-rs가 만들어졌고, b834716에서는 signaling 서버 안정성과 배포 자동화가 보강되었습니다.

🧱 시스템 구조

현재 signaling 서버의 중심은 Axum 기반 Rust 서버입니다. main.rs는 /health, /ready, /ws를 분리하고, Cloud Drop과 auth, billing, admin route까지 같은 서버 표면에 올립니다.

방 관리는 handlers/room.rs가 맡습니다. handle_join_room()은 방을 만들거나 가져오고, 기존 사용자 목록을 새 사용자에게 보내며, 기존 사용자에게 PeerJoined를 알립니다. 사용자가 나가면 leave_room_internal()이 room 사용자 목록을 정리합니다.

중요한 점은 이 서버가 파일 바이트를 직접 검증하지 않는다는 것입니다. 패킷, 암호화, ZIP64, 재정렬, 체크섬은 브라우저 worker와 pons-core-wasm의 책임입니다. signaling 서버의 책임은 그보다 앞단입니다.

🔁 사용자 플로우와 서버 플로우

사용자 입장에서 플로우는 단순합니다. 송신자는 방을 만들고 링크를 공유합니다. 수신자는 링크로 들어옵니다. 화면에 상대가 보이고 연결 상태가 바뀌면 파일 전송을 시작합니다.

서버 입장에서 같은 흐름은 더 잘게 쪼개집니다. 첫 번째는 room membership입니다. 두 번째는 signaling relay입니다. 세 번째는 connection-adjacent event입니다. TransferReady와 TransferComplete 같은 신호는 파일 바이트가 아니지만, UI가 다음 상태로 넘어가도 되는지에 영향을 줍니다.

이 경계가 어긋나면 사용자는 파일 전송 엔진의 문제인지, NAT 문제인지, 상대가 나간 것인지, 서버가 멈춘 것인지 구분하지 못합니다. 실제 파일이 아직 한 바이트도 움직이지 않았더라도, 방 참여와 협상 단계가 불안하면 사용자는 제품을 불안정하다고 판단합니다.

⚠️ 실제 실패 지점

signaling 서버에서 가장 눈에 띄는 실패 지점은 deadlock 방어였습니다. f1c69cb의 “prevent signaling room cleanup deadlocks”는 방 관리가 단순한 CRUD가 아니었다는 증거입니다.

handlers/room.rs에는 DashMap room guard를 잡은 상태에서 await나 broadcast를 호출하면 같은 shard를 다시 조회하면서 런타임 전체가 멈출 수 있다는 주석이 남아 있습니다. 그래서 필요한 상태만 복사하고 guard를 해제한 뒤 네트워크/채널 작업을 수행하도록 흐름을 바꿉니다.

또 다른 지점은 ICE fallback입니다. 3697ece의 “preserve explicit ICE fallback URLs”는 네트워크 경로 설정이 사소한 환경값이 아니라는 것을 보여줍니다. df0a6dc의 “Verify signaling protocol edge cases”도 같은 맥락입니다.

🛠️ 설계 변경

처음에는 signaling을 연결 보조 장치로 볼 수 있었습니다. 하지만 Rust 서버로 분리된 뒤에는 운영 가능한 제품 서버의 형태를 갖추기 시작했습니다. /health는 프로세스가 살아 있는지 확인하고, /ready는 Cloud Share나 billing처럼 설정된 하위 시스템이 실제로 준비되었는지를 분리해서 봅니다.

CORS도 마찬가지입니다. main.rs의 cors_layer()는 *를 허용하는 개발적 선택과 명시 origin + credentials를 쓰는 운영적 선택을 나눕니다. signaling 서버가 제품 신뢰의 일부라면, 브라우저가 어느 출처에서 어떤 credential과 함께 접근할 수 있는지 역시 제품 경계가 됩니다.

방 cleanup은 stale room이 사용자 경험을 망치지 않게 하면서도 실행 중인 signaling 흐름을 멈추지 않게 하는 운영 로직이 됩니다.

🔍 신뢰는 전송 전에 이미 시작된다

PonsWarp의 핵심은 파일 무결성이지만, 사용자가 신뢰를 느끼는 시간은 그보다 앞섭니다. 상대가 방에 들어오자마자 화면이 반응하는지, 연결 준비가 늦어질 때 상태가 납득되는지, 모바일에서 TURN fallback이 작동하는지, 서버 readiness가 배포 상태를 솔직하게 말하는지에서 이미 신뢰가 쌓이거나 깨집니다.

서버가 파일을 저장하지 않는다는 사실은 보안과 프라이버시 설명에는 도움이 됩니다. 그러나 제품 신뢰 관점에서는 “서버가 파일을 안 만진다”보다 “서버가 연결 상태를 거짓말하지 않는다”가 더 중요했습니다.

PonsWarp의 구조는 네 층으로 나뉩니다. UI는 사용자가 이해할 상태를 보여줍니다. WebRTC/worker는 실제 연결과 전송 제어를 담당합니다. pons-core-wasm은 바이트 계약을 닫습니다. signaling backend는 그 모든 흐름이 시작될 수 있는 room, peer, readiness, TURN-adjacent 정보를 관리합니다.

🧭 지금 돌아보는 판단

signaling 서버를 가볍게 본 것은 어느 정도 자연스러운 착각이었습니다. 파일 전송 제품에서 가장 어려워 보이는 문제는 대용량 바이트, 메모리, 속도, 무결성입니다. 하지만 제품으로 보이기 시작한 순간, 연결을 시작시키는 서버의 신뢰성이 같은 무게로 올라왔습니다.

44fb5ad의 Rust signaling 서버 초기 구현은 출발점이었고, b834716의 안정성/배포 보강, df0a6dc의 protocol edge case 검증, 3697ece의 ICE fallback 보존, f1c69cb의 room cleanup deadlock 수정은 모두 같은 방향을 가리킵니다. signaling은 파일을 나르지 않아도 제품 신뢰를 나릅니다.

좋은 signaling 서버는 눈에 띄지 않는 서버입니다. 상대가 자연스럽게 나타나고, 연결 준비가 조용히 진행되고, 실패하면 어디서 막혔는지 다음 판단을 줄 수 있어야 합니다.
