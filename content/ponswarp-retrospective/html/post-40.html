PonsWarp가 브라우저 앱으로 시작했다는 사실은 이 시리즈에서 계속 반복된 전제입니다.

링크를 열고, 방을 만들고, 상대가 들어오면 WebRTC DataChannel로 파일을 보냅니다. 별도 설치 없이 바로 쓰는 흐름은 제품의 가장 큰 장점이었습니다. 그런데 그 장점이 커질수록 반대쪽 한계도 선명해졌습니다.

그래서 2025년 12월 17일에 ponswarp-desktop이라는 분기가 생깁니다. 이 기록을 “웹을 포기했다”로 읽으면 너무 단순합니다. 더 정확히는 웹에서 계속 드러난 제약이 정말 브라우저 런타임의 한계인지, 아니면 전송 엔진과 제품 구조를 더 다듬어야 하는 문제인지 확인하려는 별도 실험이었습니다.

💡 이 글은 ponswarp-desktop을 성공한 제품으로 포장하지 않습니다. 2025-12-17 생성, native / QUIC / Tauri 관찰 포인트, 2026-02-18까지 보이는 활동이라는 증거 범위 안에서만 이야기합니다.

🧭 웹을 버리기 전에 분리하고 싶었던 것

브라우저 PonsWarp의 장점은 명확했습니다. 설치가 없고, 링크 공유가 쉽고, 상대에게 “앱을 먼저 깔라”고 말하지 않아도 됩니다. 파일 전송 제품에서 이 진입 비용은 작지 않습니다.

하지만 이 장점은 기술적 책임을 없애지 않습니다. 모바일과 브라우저 생명주기는 WebRTC 연결을 계속 흔듭니다. 완료 표시는 DataChannel에 밀어 넣은 바이트가 아니라 receiver가 저장하고 검증한 결과여야 합니다. 웹은 이 경계를 매번 사용자 앞에 드러냅니다.

ponswarp-desktop은 이 지점에서 나온 질문입니다. 탭 sleep, 저장 권한, 브라우저 파일 I/O, WebRTC DataChannel의 제약을 일부 걷어 내면 문제가 단순해질까. native window와 OS 파일 스트리밍, QUIC 같은 transport를 직접 만지면 더 나은 제품 리듬을 만들 수 있을까. 이 질문들이 데스크톱 분기의 출발점에 가까웠습니다.

🧱 당시 제품 상태: 이미 웹 안에서 너무 많은 것을 배웠다

데스크톱 분기가 나온 시점은 아무것도 없는 초기가 아니었습니다. 이미 PonsWarp는 메모리 폭발, 저장 완료 handshake, backpressure, RTT 기반 제어, WASM 코어 분리, Rust signaling 서버라는 여러 층을 지나고 있었습니다.

638bc83의 대용량 다운로드 메모리 폭발 방지, 21dc9ba의 수신자 저장 완료 대기 handshake, 54cf5f4의 receiver-side backpressure, 15aef19의 pons-core-wasm 초기 설정, 44fb5ad의 Rust signaling 서버 초기 구현은 모두 같은 방향을 가리킵니다.

그러니 데스크톱은 갑자기 나타난 새 장난감이 아니었습니다. 웹에서 이미 쌓인 실패 목록이 있었고, 그 실패 중 일부는 “브라우저라서 어려운 것”처럼 보였습니다. native / QUIC / Tauri라는 관찰 포인트는 그 추측을 검증하기 위한 이름들이었습니다.

⚙️ 시스템 구조로 보면 무엇이 달라지는가

브라우저 버전의 구조는 네 층으로 설명할 수 있습니다. React UI가 사용자 흐름을 만들고, WebRTC/worker가 전송을 조율하고, File System Access API와 DirectFileWriter가 저장 경계를 닫고, Rust/WASM core와 signaling backend가 바이트 계약과 방 상태를 받칩니다.

데스크톱 가설은 이 구조를 전부 버리는 것이 아니라, 일부 계층의 런타임을 바꾸는 것입니다. UI는 Tauri shell이나 native window로 감쌀 수 있습니다. 저장은 브라우저 다운로드 제약 대신 OS 파일 스트림을 직접 다룰 수 있습니다. transport는 WebRTC만이 아니라 QUIC 후보를 생각할 수 있습니다.

네이티브면 다 해결되는 것이 아닙니다. 브라우저는 설치 비용이 낮지만 권한과 생명주기가 까다롭고, 데스크톱은 파일 I/O와 네트워크 선택권이 넓어 보이지만 배포, 업데이트, OS별 차이, 보안 경고를 새로 떠안습니다.

🚧 실제 실패 지점은 브라우저만이 아니었다

웹을 포기하고 싶어지는 순간에는 눈앞의 런타임을 탓하게 됩니다. 탭이 잠들고, 저장 권한이 복잡하고, 모바일이 끊기고, DataChannel queue가 말썽이면 “앱으로 만들면 낫지 않을까”라는 생각이 자연스럽습니다.

하지만 PonsWarp의 기록을 따라가면 실패의 원인이 브라우저 하나로 닫히지 않습니다. 파일이 깨지는 문제는 패킷 순서, 버퍼 관리, 완료 판단, 크기 검증의 문제였습니다. 연결 안정성은 STUN/TURN, signaling protocol, cleanup, readiness의 문제였습니다. Cloud Drop까지 가면 사용자가 동시에 온라인이어야 한다는 제품 플로우 자체가 문제로 올라옵니다.

데스크톱 앱은 이런 문제를 한 번에 없애지 못합니다. native 파일 I/O를 얻어도 무결성 계약은 여전히 필요합니다. QUIC를 선택해도 receiver가 저장을 끝냈는지 확인해야 합니다. 설치형 앱이 되어도 상대가 앱을 깔지 않으면 직접 전송의 진입 장벽은 오히려 올라갑니다.

🔄 설계 변경: 제품 표면과 전송 코어를 따로 보게 됐다

데스크톱 분기가 남긴 가장 유용한 변화는 “웹이냐 앱이냐”라는 질문을 더 작은 질문으로 쪼갠 것입니다.

첫째, 제품 표면의 질문입니다. 사용자가 링크 하나로 들어오는 흐름이 중요한가, 아니면 설치형 앱의 안정감이 더 중요한가. 둘째, 전송 엔진의 질문입니다. WebRTC DataChannel이 제공하는 NAT traversal과 브라우저 호환성을 유지할 것인가, QUIC/native transport로 더 많은 제어권을 가져갈 것인가. 셋째, 파일 저장의 질문입니다. 브라우저 저장 API의 제한을 견딜 것인가, OS 파일 시스템을 직접 다룰 것인가.

이렇게 보면 ponswarp-desktop은 웹의 패배 선언이 아니라 설계 질문을 분리하는 장치였습니다. 무엇은 런타임 문제이고, 무엇은 전송 프로토콜 문제이고, 무엇은 제품 플로우 문제인지 더 선명하게 보게 했습니다.

⚖️ 지금 돌아보는 판단

지금 돌아보면 ponswarp-desktop를 만든 진짜 이유는 브라우저를 싫어해서가 아니라 브라우저 안에서 너무 많은 제품 약속이 충돌했기 때문입니다. 설치 없는 진입, 대용량 파일, 직접 전송, 모바일 복귀, 저장 완료 검증, 무결성, 속도 표시를 한 화면 안에서 동시에 만족시키려다 보니 “런타임을 바꾸면 더 단순해질까”라는 질문이 생겼습니다.

그 질문 자체는 필요했습니다. 웹만 붙잡고 있으면 모든 실패를 코드 부족으로 오해할 수 있습니다. 반대로 데스크톱만 바라보면 사용자 진입 비용과 배포 비용을 과소평가할 수 있습니다. 별도 분기를 만들어 본 덕분에 PonsWarp의 핵심 문제가 단순히 브라우저냐 네이티브냐가 아니라, 제품 표면과 전송 코어와 운영 책임의 조합이라는 점이 더 분명해졌습니다.

다만 증거 인덱스가 말하듯 ponswarp-desktop은 2026년 2월 18일 이후 강하게 살아 있는 주류 흐름으로 기록되어 있지 않습니다. 좋은 기술 후보가 곧 좋은 제품 경로가 되는 것은 아닙니다.
