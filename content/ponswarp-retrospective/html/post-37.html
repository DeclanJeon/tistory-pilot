PonsWarp에서 서버를 다시 보게 된 뒤, 가장 먼저 무거워진 단어는 기능명이 아니었습니다.

readiness, cleanup, production env였습니다. 셋 다 사용자가 직접 누르는 버튼은 아닙니다. 하지만 이 시점부터 이 단어들은 내부 운영 용어가 아니라 제품 신뢰를 결정하는 조건이 됐습니다.

초기에는 signaling 서버를 가볍게 볼 수 있었습니다. 방을 만들고, 두 브라우저의 offer와 answer를 이어 주고, ICE candidate를 전달하면 됩니다. 파일 데이터는 WebRTC DataChannel로 브라우저 사이를 흐르니 서버는 본편 바깥에 있는 것처럼 보입니다.

그런데 PonsWarp의 기록은 반대로 흘렀습니다. 2025-12-10 44fb5ad에서 Rust 기반 시그널링 서버가 따로 생기고, 다음 날 b834716에서 시그널링 서버 안정성 향상과 배포 자동화가 붙습니다. 훨씬 뒤의 2026-05-17 f1c69cb은 signaling room cleanup deadlock을 막는 수정입니다. 여기에 2026-05-11 58cec5b의 production readiness, 2026-06-08 d88a625의 GA4 production traffic measurement까지 이어집니다.

💡 이 글은 “운영도 중요하다”는 일반론이 아닙니다. PonsWarp에서 readiness, cleanup, production env가 왜 사용자의 연결 성공률, 실패 설명, 배포 가능성을 좌우하는 제품 구조가 됐는지를 정리합니다.

🧭 당시 제품 상태

Season 4의 흐름은 서버를 다시 보는 구간입니다. PonsWarp는 브라우저 직접 전송을 중심에 둔 제품입니다. React UI가 송수신 화면을 만들고, WebRTC와 worker가 전송을 맡고, DirectFileWriter와 WASM 코어가 저장과 바이트 검증을 받칩니다. 서버는 그 사이에서 방, peer, TURN 정보, WebSocket 연결을 다루는 경계였습니다.

이 구조에서 서버가 멈추거나 준비되지 않았다는 사실은 단순한 백엔드 장애로 끝나지 않습니다. 사용자는 “방에 들어갔는데 상대가 안 보인다”, “링크는 열리는데 연결이 안 된다”, “모바일에서는 되는 듯하다가 끊긴다”처럼 경험합니다. 문제는 서버에 있지만 증상은 제품 화면에 나타납니다.

그래서 /health와 /ready는 운영자용 엔드포인트만이 아닙니다. 서비스가 지금 트래픽을 받아도 되는지, 필수 설정이 빠지지 않았는지, 배포된 프로세스가 단순히 살아 있는 것을 넘어 제품 경로를 감당할 수 있는지를 나누는 기준입니다.

🧱 시스템 구조: signaling 서버가 품은 것

PonsWarp의 반복 4층 구조에서 이 글의 위치는 Core and backend입니다. 여기에는 ponswarp-signaling-rs의 /health, /ready, /ws, auth, billing, state, cleanup이 들어갑니다. /ws는 사용자 플로우의 입구이고, state와 cleanup은 그 입구가 다음 사용자에게도 열려 있게 만드는 조건이며, /ready는 운영 환경이 그 책임을 맡을 준비가 되었는지 확인하는 표면입니다.

처음의 signaling은 request-response API보다 세션 상태에 가깝습니다. 방이 있고, sender와 receiver가 붙고, WebSocket이 유지되고, ICE candidate가 시간차로 오고 갑니다. 여기에 TURN 설정까지 들어오면 서버는 단순 relay가 아니라 연결 가능성을 높이기 위한 설정 공급자가 됩니다.

문제는 세션 상태에는 반드시 수명이 있다는 점입니다. 사용자가 탭을 닫을 수 있고, 모바일 브라우저가 background로 내려갈 수 있고, 네트워크가 끊길 수 있고, WebSocket 종료 이벤트가 깔끔하게 오지 않을 수도 있습니다. 이때 방과 peer 상태가 남으면 다음 연결은 이상한 상태에서 시작합니다.

⚠️ 실제 실패 지점: 죽은 상태가 살아 있는 척할 때

P2P 서비스에서 실패는 종종 조용합니다. 방은 만들어졌는데 상대가 안 붙거나, 붙은 것처럼 보이는데 ICE negotiation이 끝나지 않거나, 한쪽 WebSocket이 끊겼는데 room state가 남아 있거나, TURN 설정이 production 환경에서 잘못 조합돼 연결이 실패합니다.

이런 실패는 UI에서 정확히 설명하기 어렵습니다. 사용자는 내부 room map이나 lock 상태를 보지 않습니다. 그래서 서버가 stale room을 얼마나 빨리 정리하는지, cleanup이 다른 상태 lock과 충돌하지 않는지, readiness가 잘못된 환경을 배포 전에 걸러 주는지가 중요해집니다.

f1c69cb fix: prevent signaling room cleanup deadlocks는 구현 내부 문제처럼 보이지만, signaling 서버에서는 제품 상태가 멈춘다는 뜻이기도 합니다. cleanup이 막히면 죽은 방이 남고, 죽은 방이 남으면 사용자는 새 연결에서 이해하기 어려운 실패를 만납니다.

🔧 설계 변경: 준비 상태를 코드 밖으로 꺼내기

readiness가 중요해지는 순간, 설정은 더 이상 .env에 숨은 부가 정보가 아닙니다. WebRTC 제품에서 production env는 실제 연결 경로의 일부입니다. STUN/TURN URL, credential 발급, WebSocket origin, 배포된 서버 주소, Cloud Drop 경로, traffic measurement가 모두 사용자가 만나는 흐름에 영향을 줍니다.

초기 PonsWarp에서도 production logging과 STUN/TURN 보강은 빠르게 등장했습니다. 이후 Rust signaling 서버가 생기고 배포 자동화가 붙은 것은 같은 방향입니다. 개발 환경에서는 한 브라우저와 한 네트워크에서 통과하던 가정이 production에서는 깨집니다. 회사망, 모바일 NAT, 브라우저 background, 지역별 relay, 잘못된 환경 변수는 모두 제품 실패로 번역됩니다.

그래서 readiness는 “서버가 켜졌는가”보다 더 좁고 엄격해야 합니다. WebSocket을 받을 수 있는지, 필수 환경 변수가 있는지, TURN fallback이 실제 URL로 보존되는지, Cloud Drop이나 계정/과금 경로가 켜져 있다면 그 경로가 사용자를 속이지 않는지 확인해야 합니다.

📊 운영 언어가 제품 언어로 바뀌는 순간

운영 단어묻는 질문제품 영향
readiness지금 사용자를 받아도 되는가준비되지 않은 배포가 연결 실패로 노출되는 일을 막음
cleanup죽은 상태가 다음 사용자를 방해하지 않는가stale room과 peer state가 새 연결을 오염시키지 않게 함
production env로컬 가정이 실제 네트워크에서도 성립하는가TURN, WebSocket, Cloud Drop, 측정 경로를 제품 조건으로 검증함

이 질문들은 모두 사용자 플로우로 돌아옵니다. 보내는 사람은 방을 만들고 링크나 QR을 공유합니다. 받는 사람은 들어와서 연결을 기다립니다. 서버는 두 사용자가 서로를 찾게 하고, 필요한 연결 정보를 주고, 죽은 상태를 치우고, 준비되지 않은 배포가 트래픽을 받지 않게 해야 합니다.

🚫 운영을 나중에 붙이면 된다는 말은 맞지 않았다

처음부터 모든 운영 체계를 완성해야 한다는 뜻은 아닙니다. 작은 제품은 작은 운영으로 시작할 수 있습니다. 하지만 PonsWarp처럼 브라우저 P2P, TURN, WebSocket room state, Cloud Drop 가능성, 모바일 resume이 얽히는 서비스에서는 운영을 완전히 뒤로 미루기 어렵습니다.

특히 signaling 서버는 파일 데이터를 저장하지 않는다는 이유로 가볍게 보이기 쉽습니다. 하지만 실제로는 연결의 첫 신뢰 조건을 쥐고 있습니다. 서버가 방 상태를 잘못 들고 있거나, cleanup이 멈추거나, production env가 잘못 배포되면 파일 전송 엔진과 WASM 코어가 아무리 정교해도 사용자는 그 단계까지 가지 못합니다.

서버가 파일을 안 들고 있으니 핵심이 아니다가 아니라, 서버가 사용자를 연결하지 못하면 핵심 전송은 시작도 못 한다에 가까워졌습니다.

🧭 지금 돌아보는 판단

이 시점의 교훈은 화려하지 않습니다. readiness는 있어야 하고, cleanup은 조심해야 하고, production env는 검증돼야 합니다. 너무 당연해 보입니다. 하지만 PonsWarp에서는 이 당연한 것들이 늦게야 제품 언어로 들어왔습니다.

브라우저끼리 직접 파일을 보내는 경험은 여전히 PonsWarp의 중심입니다. 다만 직접 전송이라는 말이 서버 책임을 지워 주지는 않습니다. 방을 만들고, 상대를 찾고, TURN 정보를 주고, 죽은 상태를 치우고, 준비된 배포만 트래픽을 받게 하는 일은 모두 그 직접 전송을 가능하게 하는 바닥입니다.

그래서 post-37의 제목에 있는 세 단어는 운영 체크리스트가 아니라 제품화의 기준입니다. readiness는 사용자를 받을 준비, cleanup은 다음 사용자를 위한 상태 위생, production env는 현실 네트워크와 배포 환경을 제품 구조 안으로 끌어들이는 일입니다.
