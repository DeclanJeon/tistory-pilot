PonsWarp 회고의 마지막 질문은 “성공했나 실패했나”가 아닙니다. 더 유용한 질문은 지금 같은 문제를 다시 만난다면 무엇을 그대로 남기고, 무엇을 더 일찍 버리고, 무엇을 아예 다른 순서로 만들 것인가입니다.

이 시리즈에서 반복해서 본 PonsWarp의 중심은 대용량 파일 전송이었습니다. 하지만 기록을 따라가면 단순한 속도 프로젝트가 아니었습니다. 2025년 11월 20일 첫 커밋 이후 메모리 폭발, 저장 완료 handshake, TURN, AIMD, 파일 손상, backpressure, WASM 코어, Rust signaling, Cloud Drop, 과금, 모바일 복귀, GA4 계측까지 흘러갔습니다. 처음에는 “브라우저에서 큰 파일을 보내자”였지만, 끝에서는 “사용자가 언제 어떤 조건에서 파일을 믿고 받을 수 있는가”가 더 큰 문제가 되었습니다.

💡 이 글은 PonsWarp를 다시 만들 수 있다는 가정 아래 쓰지만, 새 구현 세부를 꾸며 내지는 않습니다. 근거는 `series-plan.md`, `evidence-index.md`, 그리고 앞선 회고에서 이미 다룬 커밋 흐름입니다. 다시 만든다면의 의미는 미래 예언이 아니라, 이미 남은 기록을 기준으로 판단의 우선순위를 다시 세워 보는 일입니다.

🧭 먼저 남길 것: 설치 없는 진입과 신뢰 계약

다시 만들어도 버리지 않을 첫 번째 요소는 링크 기반 진입입니다. PonsWarp가 웹으로 시작한 이유는 분명했습니다. 파일을 보내야 하는 사람에게 설치, 계정, 업데이트를 먼저 요구하지 않는 흐름은 강한 제품 장점입니다. 상대도 링크를 열고 바로 들어올 수 있어야 직접 전송의 의미가 살아납니다.

두 번째로 남길 것은 저장 완료를 진짜 완료로 보는 계약입니다. 2025-11-21 21dc9ba의 수신자 저장 완료 대기 handshake는 이 시리즈 전체에서 중요한 분기점이었습니다. 전송 완료 표시가 sender queue 기준이면 사용자는 속을 수 있습니다. receiver가 파일을 저장하고 검증한 뒤에야 완료라고 말해야 합니다. 이 원칙은 WebRTC든 Cloud Drop이든 데스크톱이든 바뀌지 않습니다.

세 번째는 무결성을 기능보다 앞에 두는 태도입니다. db175bf, 8aff234, 4650d02로 이어진 파일 손상 수정 기록은 “빠르게 보냈다”와 “제대로 받았다”가 다르다는 사실을 보여 줍니다. 다시 만든다면 속도 지표는 더 늦게 전면에 세우고, 크기 검증, 순서 보장, 재정렬, signature, 복구 가능성을 먼저 제품 언어로 고정했을 것입니다.

네 번째는 코어 경계입니다. pons-core-wasm을 따로 만든 선택은 무거웠지만 의미가 있었습니다. ZIP64, reordering buffer, Merkle tree, file signature, crypto, zero-copy pool 같은 영역은 화면 코드 안에서 섞이면 오래 버티기 어렵습니다. 다시 만든다면 Rust/WASM 코어를 더 작게 시작하더라도, 바이트 계약을 UI와 분리하는 방향은 남깁니다.

🧱 당시 제품 상태를 다시 보면

PonsWarp는 어느 순간 네 층짜리 제품이 되었습니다. React UI와 방/링크 흐름이 있고, WebRTC DataChannel과 worker 기반 전송 엔진이 있고, File System Access API와 DirectFileWriter로 대표되는 저장 경계가 있고, pons-core-wasm과 ponswarp-signaling-rs가 core/backend를 받쳤습니다.

이 구조 자체는 틀렸다고 보기 어렵습니다. 문제는 각 층이 동시에 커졌다는 데 있었습니다. 전송 안정화가 끝나기 전에 UI 약속이 커졌고, 직접 전송의 한계가 정리되기 전에 Cloud Drop이 붙었고, Cloud Drop이 붙자 무료/유료 정책과 entitlement flow가 따라왔습니다. 거기에 데스크톱 분기까지 생기면서 “무엇을 검증하려는 제품인가”라는 질문이 자주 흐려졌습니다.

다시 만든다면 계층은 남기되 출시 순서를 바꿉니다. 첫 단계는 Direct transfer의 신뢰 조건만 좁게 잡습니다. 두 번째 단계에서 모바일 복귀와 resume을 붙입니다. 세 번째 단계에서 Cloud Drop을 별도 제품 플로우로 분리합니다. 결제와 entitlement는 Cloud Drop의 보존 기간, 용량, 재개 가능성, 삭제 정책이 먼저 선명해진 뒤에 붙입니다.

⚙️ 시스템 구조에서 버릴 것

가장 먼저 버릴 것은 “한 런타임이 모든 문제를 해결한다”는 기대입니다. 브라우저가 답답하다고 데스크톱으로 가면 저장 I/O와 transport 선택권은 넓어질 수 있습니다. 하지만 설치 비용, 배포, OS별 차이, 보안 경고가 새로 생깁니다. WebRTC가 어렵다고 Cloud Drop으로 가면 동시 접속 문제는 줄어들지만 저장 비용, 만료 정책, 계정/결제, abuse 대응이 올라옵니다.

두 번째로 버릴 것은 성급한 표면 확장입니다. Cloud Drop 자체는 필요했습니다. 사용자가 동시에 온라인이어야 한다는 조건은 파일 전송 제품에서 큰 제약입니다. 2026-05-12 4847872의 async cloud drops, 2026-05-14 3628858의 resumable multipart uploads는 이 문제를 실제 제품 흐름으로 옮긴 기록입니다. 다만 다시 만든다면 pricing page, entitlement, 무료 정책을 더 늦게 붙였을 것입니다. 제품 약속이 안정되기 전에 돈의 표면이 먼저 나오면 설계 판단이 빨리 굳습니다.

세 번째로 버릴 것은 지표 없는 자신감입니다. 2026-06-08 d88a625의 GA4 production traffic measurement는 늦게 붙은 중요한 장치였습니다. 다시 만든다면 계측은 출시 뒤 장식이 아니라 초기 제품 판단의 일부로 둡니다. 직접 전송 실패율, TURN fallback 비율, 모바일 background 후 복귀율, Cloud Drop 재개 성공률, 저장 완료까지 걸린 시간을 먼저 봐야 했습니다.

🚧 실제 실패 지점: 기술보다 제품 조건이 늦게 정리됐다

PonsWarp의 실패 지점은 “WebRTC가 어렵다” 하나로 닫히지 않습니다. WebRTC는 어려웠지만, 더 큰 문제는 제품 조건이 뒤늦게 드러났다는 점입니다. 사용자가 둘 다 온라인이어야 하는가. 모바일에서 잠깐 나갔다 돌아와도 이어져야 하는가. 10GB를 무료로 줄 때 비용과 abuse는 어떻게 다룰 것인가. 저장이 끝나기 전 완료라고 말하지 않으려면 UI는 어떤 상태를 보여 줘야 하는가.

이 질문들이 늦게 올라오면 코드는 방어적으로 커집니다. AIMD, RTT 제어, backpressure, reordering buffer, partial recovery는 모두 필요한 장치였지만, 사용자가 기대하는 제품 조건이 먼저 좁혀졌다면 일부는 더 단순한 형태로 시작할 수 있었습니다. 반대로 조건을 좁히지 않은 채 “대용량, 빠름, 무료, 모바일, Cloud, 결제, 데스크톱 가능성”을 함께 들고 가면 모든 계층이 동시에 압박을 받습니다.

그래서 다시 만든다면 첫 화면부터 더 솔직했을 것입니다. Direct transfer는 빠르고 설치가 없지만 양쪽이 온라인이어야 한다. Cloud Drop은 비동기 수신이 가능하지만 보존 기간과 용량 정책이 있다. 모바일은 복귀를 지원하되 네트워크와 브라우저 생명주기에 따라 재연결 단계가 보인다. 이런 말은 마케팅 문장으로는 덜 매끈하지만, 제품을 오래 살리는 문장입니다.

🔄 설계 변경: Direct와 Cloud를 같은 제품 안의 다른 계약으로 보기

PonsWarp를 다시 만든다면 Direct transfer와 Cloud Drop을 같은 전송 버튼의 옵션처럼 다루지 않았을 것입니다. 둘은 사용자에게 주는 약속이 다릅니다.

Direct transfer는 “지금 둘이 연결되어 있고, 파일이 브라우저 사이로 직접 흐르며, 저장 완료를 확인한다”는 계약입니다. 여기서는 WebRTC, STUN/TURN, backpressure, 저장 handshake, 무결성 검증이 핵심입니다. 빠른 시작과 설치 없는 흐름이 장점이고, 동시 접속과 브라우저 생명주기가 비용입니다.

Cloud Drop은 “보내는 사람이 먼저 올려 두고, 받는 사람이 나중에 받으며, 서버 저장과 만료 정책을 신뢰한다”는 계약입니다. 여기서는 resumable multipart upload, object storage, entitlement, 보존 기간, 삭제 정책, abuse 대응이 핵심입니다. 비동기성이 장점이고, 운영 비용과 계정/결제 표면이 비용입니다.

둘을 한 서비스 안에 둘 수는 있습니다. 다만 다시 만든다면 내부 구조와 글자부터 분리합니다. Direct는 live transfer, Cloud Drop은 delayed delivery입니다. 같은 파일 전송처럼 보이지만 실패 모드와 운영 책임이 다릅니다. 이 차이를 UI와 가격 정책과 기술 구조가 모두 알아야 합니다.

⚖️ 지금 돌아보는 판단

지금 다시 만든다면 PonsWarp에서 남길 것은 집착입니다. 파일이 깨지면 안 된다는 집착, 완료를 쉽게 말하지 않겠다는 집착, 브라우저라는 낮은 진입 비용을 포기하지 않으려는 집착은 남길 만합니다. 이 집착이 있었기 때문에 memory blow-up, save-complete handshake, backpressure, WASM core, signaling hardening 같은 기록이 나왔습니다.

버릴 것은 한 번에 제품이 되려는 조급함입니다. 좋은 전송 엔진, 좋은 저장 계약, 좋은 비동기 배송, 좋은 과금 구조, 좋은 데스크톱 후보는 서로 연결될 수 있지만 같은 속도로 익지 않습니다. 다시 만든다면 “직접 전송을 믿을 수 있게 만든다”와 “나중에 받을 수 있게 만든다”를 더 분명히 나누고, 결제와 데스크톱은 그 다음 검증으로 미룹니다.

그리고 더 일찍 넣을 것은 운영 언어입니다. TURN은 비용입니다. Cloud Drop은 저장 책임입니다. 모바일 resume은 UX가 아니라 생명주기 대응입니다. GA4 같은 계측은 마케팅용 숫자가 아니라 제품 판단의 계기판입니다. 이 언어가 초기에 들어오면 기술 선택도 덜 과열됩니다.

마지막 글에서 남는 판단은 단순합니다. PonsWarp를 다시 만든다면 더 작게 시작했을 것입니다. 하지만 덜 진지하게 만들지는 않았을 것입니다. 오히려 “빠른 파일 전송”이라는 큰 말보다 “받는 사람이 실제로 저장하고 다시 열 수 있는 파일”이라는 좁은 말을 더 오래 붙잡았을 것입니다. 그 좁은 말이 이 프로젝트가 남긴 가장 쓸 만한 기준입니다.
