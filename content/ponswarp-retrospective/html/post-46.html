PonsWarp에서 결제를 붙이는 일은 처음에는 비교적 분리된 기능처럼 보였습니다.

Cloud Drop을 유료 기능으로 만들고, pricing page를 세우고, 결제 provider를 붙이고, 결제가 끝나면 더 큰 업로드나 더 긴 보관을 열어 주면 되는 일처럼 보였습니다. 하지만 실제로 어려웠던 것은 PayPal 버튼 자체가 아니었습니다. 더 어려운 것은 checkout 이후의 상태를 제품 권한으로 안전하게 바꾸는 일이었습니다.

파일 전송 제품에서 결제는 일반적인 SaaS 구독 화면보다 더 까다롭게 느껴집니다. 사용자는 “돈을 냈다”는 사실보다 “지금 이 파일을 보낼 수 있는가”를 먼저 확인합니다. 결제는 독립된 화면에서 끝나지 않고 Cloud Drop 업로드, 보관 시간, 용량 제한, 다운로드 링크, 실패 안내로 바로 이어집니다.

💡 이 글은 PayPal이 Stripe보다 좋다거나 나쁘다는 비교가 아닙니다. Stripe Checkout, PayPal billing, Free plan 정책, gated account/billing surface 비활성화가 왜 같은 제품화 압력 안에 있었는지를 정리합니다.

🧭 당시 제품 상태: Cloud Drop이 상품이 되기 시작했다

PonsWarp의 초반 핵심은 브라우저 간 직접 전송이었습니다. WebRTC DataChannel, sender/receiver worker, DirectFileWriter, pons-core-wasm, signaling server가 맞물려 “상대가 온라인일 때 바로 보내는” 흐름을 만들었습니다.

4847872의 async Cloud Drop은 delayed downloads를 가능하게 한 자연스러운 확장이었습니다. 사용자는 파일을 올려 두고 링크를 공유할 수 있고, 수신자는 나중에 받을 수 있습니다. 하지만 이 순간 PonsWarp는 순수한 P2P 도구에서 저장과 운영 비용을 가진 서비스로 바뀝니다.

b6f3ea8의 Cloud Drop pricing page는 그 변화가 UI에도 드러난 지점입니다. 가격 페이지가 생긴다는 것은 무료로 어디까지 허용할지, 유료 사용자는 무엇을 더 얻는지, 보관 시간과 용량 제한을 어떤 말로 설명할지 정해야 한다는 뜻입니다.

💳 Checkout은 시작일 뿐이었다

결제 provider를 붙이면 화면에서는 checkout URL 하나가 가장 눈에 띕니다. 사용자가 버튼을 누르고 PayPal로 이동하고, 결제를 마치고 돌아오면 된다고 생각하기 쉽습니다. 하지만 서비스 입장에서는 그 순간이 끝이 아니라 시작입니다.

브라우저 redirect는 진실의 원천이 될 수 없습니다. 사용자가 성공 URL로 돌아왔다고 해서 서버가 안전하게 결제 완료를 반영했다고 단정할 수 없습니다. 외부 provider의 webhook, 서버의 검증, 내부 상태 전이가 맞아야 합니다.

Webhook은 중복되거나 늦게 올 수 있습니다. 같은 결제 이벤트가 여러 번 도착해도 권한이 중복 발급되면 안 되고, 늦게 도착해도 사용자가 이미 실패처럼 느끼지 않도록 상태를 설명해야 합니다. 3628858의 resumable multipart uploads까지 고려하면 유료 권한은 긴 업로드 중에도 일관되게 해석되어야 합니다.

🔐 Entitlement는 단순 플래그가 아니었다

PonsWarp의 entitlement는 “이 사용자가 유료인가”보다 넓은 질문이었습니다. Cloud Drop에서는 무료 10GB / 24시간 같은 정책과 유료 정책이 사용자 행동을 직접 가릅니다. 업로드 가능 여부, 보관 시간, 다운로드 링크, 만료 안내가 모두 entitlement의 일부가 됩니다.

a004c91의 Free plan first-class cloud policy는 중요합니다. 무료 정책을 단순 fallback으로 두면 제품 설명이 흐려집니다. 반대로 Free plan을 first-class로 올리면 유료 전환을 하지 않은 사용자도 명확한 계약 안에 들어옵니다.

⚠️ PayPal로 바꾸면 쉬워지는 줄 알았던 부분

f8f2120은 Cloud Drop entitlements를 Stripe Checkout에서 발급하는 흐름을 보여 주고, 2e4593d는 Cloud Drop billing을 PayPal로 라우팅한 기록입니다. 이 흐름을 provider 교체로만 읽으면 핵심을 놓칩니다.

Provider가 바뀌면 결제 객체 이름, checkout 생성 방식, webhook payload, 검증 방식, 실패 코드가 달라집니다. 하지만 제품이 지켜야 할 계약은 같습니다. 돈을 냈는데 Cloud Drop이 열리지 않으면 안 됩니다. 돈을 내지 않았는데 유료 권한이 열려도 안 됩니다. 같은 webhook이 두 번 와도 한 번의 권한 전이로 끝나야 합니다.

결국 PayPal 작업은 “결제 수단 추가”라기보다 외부 provider의 불확실성을 PonsWarp 내부의 entitlement 상태로 번역하는 작업에 가까웠습니다.

🔄 시스템 구조가 더 무거워진 이유

이 구간의 시스템은 네 층으로 나눠 보면 더 선명합니다. 1층은 Product and UI입니다. React/Vite 기반 화면, CloudSenderView, pricing page, account/billing surface가 사용자의 선택과 상태를 설명합니다.

2층은 Cloud Drop 업로드 흐름입니다. 파일 선택, 업로드 시작, 진행률, 실패 재시도, 다운로드 링크 생성이 여기에 놓입니다. 3628858의 resumable multipart uploads는 이 층이 단순 POST 업로드가 아니라 긴 시간 동안 상태를 유지해야 하는 흐름임을 보여 줍니다.

3층은 entitlement와 billing backend입니다. checkout 생성, PayPal callback/webhook 처리, drop pass 또는 subscription 성격의 권한 발급, 사용량과 만료 정책이 여기에 있습니다. 이 층은 provider API를 감싸는 adapter가 아니라 제품의 권한 원장에 가깝습니다.

4층은 운영과 관찰입니다. /health, /ready, database, cleanup, production env, 그리고 이후 d88a625의 GA4 measurement까지 이어지는 영역입니다. 결제와 entitlement는 운영 관찰 없이 안전하다고 말하기 어렵습니다.

🧱 실제 실패 지점: 결제보다 상태 설명이 어려웠다

PonsWarp의 제품화 구간에서 실제로 어려웠던 것은 기능 수가 부족한 것이 아니었습니다. Cloud Drop, pricing page, Stripe Checkout, PayPal billing, multipart resumable upload, Free plan, gated surface rollback, GA4 measurement가 짧은 시간 안에 이어졌습니다.

사용자는 “나는 지금 무료인가, 유료인가”, “이 파일은 몇 GB까지 가능한가”, “결제하면 지금 업로드가 이어지는가”, “상대는 언제까지 받을 수 있는가”를 제품 문장으로 이해해야 합니다. 212d751이 gated account and billing surfaces를 비활성화한 것은 이 맥락에서 보수적인 판단으로 읽힙니다.

🧭 지금 돌아보는 판단

지금 돌아보면 PayPal 자체가 특별히 어려웠다기보다, PayPal을 붙일 만큼 제품이 서비스가 되어 버린 것이 어려웠습니다. 직접 전송만 있을 때의 실패는 네트워크, 브라우저, 저장 경계의 실패였습니다. Cloud Drop과 결제가 들어온 뒤의 실패는 권한, 정책, 운영, 사용자 기대의 실패가 됩니다.

PonsWarp는 이미 기술적으로 많은 문제를 다뤘습니다. 하지만 결제와 entitlement는 “해결하면 끝나는 기능”이 아니라 계속 운영해야 하는 계약이었습니다. provider를 바꿔도 이 계약은 사라지지 않습니다.

제품이 돈을 받기 시작하려면 checkout보다 먼저 entitlement 문장이 닫혀 있어야 합니다. 누가, 언제, 무엇을, 얼마만큼, 얼마나 오래 쓸 수 있는지가 닫히지 않으면 checkout은 오히려 혼란을 증폭합니다.
